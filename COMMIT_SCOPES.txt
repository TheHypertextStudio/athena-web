# One allowed Conventional Commit scope per line.

# A scope names the product/domain area a change lands in. If a change is cross-cutting and
# doesn't belong to one area — e.g. it touches the exports/module boundary across many
# domains/packages at once — omit the scope entirely rather than reaching for the closest-sounding
# one. `dx` is not a catch-all for "internal/technical work"; see its own comment below.
admin
agents
athena
api
auth
billing

design
docs
# editor: the typed surfaces themselves — the document, and the inline title and summary fields
# wherever they appear. A field's own behaviour and geometry belong here even when the bug is only
# visible on one kind of record; that record's scope owns what surrounds the field, not the field.
editor
# dx: the LOCAL DEVELOPER'S day-to-day tooling and workflow only — lint config, CI, build
# scripts, the dev server, editor/IDE setup. It is not for the product's own code, including
# internal package/module structure, exports, or naming (that work is either scoped to the
# domain/package it changes, or left unscoped if it's cross-cutting).
dx
hub
# initiatives: an initiative as a person meets it — opening one, reading it, changing its
# properties. Pairs with `projects`: the record is the section, so a change to the page you open an
# initiative into belongs here rather than to whatever component happens to draw it. A change
# spanning several kinds of record takes the one it was found on.
initiatives
