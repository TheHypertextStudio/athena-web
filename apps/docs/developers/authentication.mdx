Docket runs an OAuth 2.1 resource server, with the authorization server on the same origin at
`/api/auth/*`.

## Discovery

Fetch these two and you need nothing else to start.

| Document | Path | Standard |
| --- | --- | --- |
| Protected Resource Metadata | `/.well-known/oauth-protected-resource/mcp` | RFC 9728 |
| Authorization Server Metadata | `/.well-known/oauth-authorization-server` | RFC 8414 |

The AS metadata advertises the authorize, token, and registration endpoints, `S256` for
`code_challenge_method`, and URL-form client IDs.

## Registering a client

<Tabs>
  <Tab title="Dynamic registration">
    Classic Dynamic Client Registration, RFC 7591:

    ```http
    POST /api/auth/mcp/register
    ```

    Returns a `client_id`.
  </Tab>
  <Tab title="Client ID Metadata Document">
    Serve a metadata document at an HTTPS URL and use that URL as your `client_id`. Register
    nothing ahead of time.

    Docket fetches, DNS-checks, and validates it during the authorize preflight, then shows the
    validated `client_name` and `logo_uri` on the consent screen.
  </Tab>
</Tabs>

## The authorization code flow with PKCE

<Steps>
  <Step title="Authorize">
    Send the browser to `/oauth/authorize` with `client_id`, `scope`, and `code_challenge`. Docket
    routes anyone unauthenticated through `/sign-in` first.
  </Step>
  <Step title="Exchange the code">
    PKCE, with `resource` set to the MCP resource URL per RFC 8707.
  </Step>
  <Step title="Call with the token">
    `Authorization: Bearer <token>` on every request.
  </Step>
</Steps>

## Token lifetimes

| | |
| --- | --- |
| Access token | 15 minutes |
| Refresh token | 30 days |

## Scopes

Four capability scopes, plus `offline_access`.

| Scope | Grants |
| --- | --- |
| `work:read` | Read work. Run views, search, read tasks, projects, and Hub resources. The usual default. |
| `work:write` | Create and update work: tasks, projects, initiatives, comments, updates. |
| `agents:run` | Manage agents. Trigger sessions, approve or reject proposed actions. |
| `connectors:link` | Link external items, such as GitHub and Linear references, onto work. |
| `offline_access` | Issue a refresh token. |

Ask for the narrowest set that does the job. People decline a read-only integration that asks for
`work:write` and `agents:run`.

### Insufficient scope

A `work:read` token calling a write operation gets a `403` with:

```http
WWW-Authenticate: Bearer error="insufficient_scope"
```

Re-run the authorization flow for the wider scope, then retry the call.

## The limit on every token

<Warning>
  **A token can never do more than the human who consented to it.**
</Warning>

Scopes gate first, then that person's own grants. A `work:write` token held by someone with `view`
on "Launch v2" cannot write to it. People revoke in **Settings → Connected apps**, which deletes
the consent and its access tokens. Build for it: run the authorization flow again.

## What is not available

No API keys. No long-lived static credentials. The web app's Better Auth session cookie serves
first-party surfaces only.
