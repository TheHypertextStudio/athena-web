Docket ships a first-party [Model Context Protocol](https://modelcontextprotocol.io) server. Any
MCP-capable agent — Claude Code, Claude Desktop, claude.ai, Codex, Cursor, Windsurf, or anything
else speaking Streamable HTTP and OAuth 2.1 — can read and act on your workspace.

<Tip>
  The in-app version of this page is **Settings → Connected apps**, which shows the same snippets
  with your deployment's URL already filled in.
</Tip>

## The endpoint

```
https://docket-api.hypertext.studio/mcp
```

Note the **API** origin rather than the web app origin. Substitute your own deployment's MCP URL
throughout this page if you self-host.

The endpoint speaks MCP Streamable HTTP: `POST` for messages, `GET` for the server-to-client
stream, `DELETE` to end a session. Requests are stateless, so a client can work without ever
holding a session. `initialize` returns an `Mcp-Session-Id` anyway, and presenting it unlocks the
notification channel described below.

## Client setup

<Tabs>
  <Tab title="Claude Code">
    ```sh
    claude mcp add docket https://docket-api.hypertext.studio/mcp
    ```

    Run once in any terminal; the server is then available globally across projects. Claude Code
    walks the OAuth flow in your browser on first use.
  </Tab>
  <Tab title="Claude Desktop">
    1. In the chat bar, open the menu (**+**) and select **Connectors → Manage Connectors**.
    2. Click **+** and select **Add custom connector**.
    3. Enter "Docket" as the name and paste the MCP URL.
    4. Click **Add** — your browser opens to complete authorization.
    5. Sign in to Docket and approve the requested permissions.
  </Tab>
  <Tab title="claude.ai">
    **Settings → Connectors → Add custom connector**, paste the MCP URL, and complete the browser
    authorization. Same flow as Claude Desktop.
  </Tab>
  <Tab title="Codex">
    Add to `~/.codex/config.toml`, or to `.codex/config.toml` in a trusted repo for per-project
    scope:

    ```toml
    [mcp_servers.docket]
    url = "https://docket-api.hypertext.studio/mcp"
    ```

    Then authorize:

    ```sh
    codex mcp login docket
    ```
  </Tab>
  <Tab title="Cursor">
    Use the install deep link from **Settings → Connected apps** in Docket, or add to
    `~/.cursor/mcp.json`:

    ```json
    { "mcpServers": { "docket": { "url": "https://docket-api.hypertext.studio/mcp" } } }
    ```
  </Tab>
  <Tab title="Windsurf">
    Add to `~/.codeium/windsurf/mcp_config.json` — note `serverUrl` rather than `url`:

    ```json
    { "mcpServers": { "docket": { "serverUrl": "https://docket-api.hypertext.studio/mcp" } } }
    ```
  </Tab>
</Tabs>

### Anything else

Point any MCP-compatible client at the URL. Clients implementing the MCP authorization
specification handle registration, consent, and token refresh on their own through the
[discovery documents](/developers/authentication#discovery).

## Authorization, briefly

The server is an OAuth 2.1 resource server. A connecting client registers (via DCR or a URL-form
client ID), sends you to Docket's consent screen, and exchanges the code with PKCE for a token
audience-bound to the `/mcp` resource URL.

Scopes are the first gate; your own roles and grants remain binding underneath. **A token can
never do more than you can.**

Full detail in [Authentication](/developers/authentication).

## Names work anywhere IDs do

This is the single most useful thing to know when writing prompts against this server.

```json
{ "teamId": "Platform", "assigneeId": "Sarah", "state": "In Review" }
```

All three resolve server-side. Matching runs exact → prefix → substring and accepts only an
unambiguous hit. An ambiguous name comes back listing the candidates rather than guessing, and an
unknown workflow state comes back listing the team's legal ones.

Agents therefore rarely need to look an ID up before acting.

## Live updates

A client that completes `initialize` receives an `Mcp-Session-Id` and can hold a `GET /mcp` stream
open to receive:

- `notifications/resources/updated` for anything it has subscribed to
- `notifications/tools/list_changed` when a grant change alters what it may call
- `notifications/message` at whatever level it sets via `logging/setLevel`

<Note>
  Delivery is best-effort and never replayed. Treat an update as a prompt to re-read rather than as
  the data itself.
</Note>

`DELETE /mcp` ends the session.

## Letting Athena use another MCP server

The relationship runs both ways. Athena can act as an MCP **client** for a workspace.

Go to **Settings → Connections → MCP connectors**, enter the server URL, choose **Sign in and
approve access**, and finish the provider's browser approval. Docket verifies `tools/list` before
Athena receives any of that server's tools, and namespaces them as `<connector>__<tool>` so
external tools cannot collide with Docket's own.

The connection follows the current MCP OAuth flow — protected-resource discovery, authorization-
server discovery, PKCE, the RFC 8707 resource indicator, and URL-form client IDs where the
provider advertises them. Docket falls back to dynamic client registration only when a server does
not advertise CIMD.

Credentials, registration state, and PKCE state are encrypted at rest. Athena receives the
resulting server tools, never a raw user token.

<Warning>
  External tools do not bypass Docket's approval policy. A tool's declared annotations and the
  normal action policy still decide whether Athena may execute it or must
  [ask you first](/guides/athena/proposals-and-approvals).
</Warning>

## Revoking access

**Settings → Connected apps** lists every client you have consented to, with per-client revoke that
deletes the consent and its access tokens. Access tokens also expire on their own after 15
minutes, and refresh tokens after 30 days.

## Self-hosting

The OAuth authorization and resource server is core functionality — always on, in every deploy,
with no MCP-specific configuration required.

Its URLs derive from configuration every deploy already sets: the issuer from the API URL, the
resource from `${API_URL}/mcp`, and the login page from `${WEB_URL}/sign-in`. Override one only to
change its derivation, such as a non-standard sign-in route.

Registration, token exchange, introspection, revocation, the JWKS, and both discovery documents
are public by design under RFC 7591, 6749, 7662, 7009, 8414, and 9728 — a client authenticates
itself rather than carrying a session cookie. They run under an open, credential-free CORS policy,
so any MCP client's web UI can call them with nothing added to an allowlist.
