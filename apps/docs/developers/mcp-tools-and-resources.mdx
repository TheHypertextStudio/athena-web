The MCP server exposes **25 tools**, a set of `docket://` resources, and 3 prompts.

Every tool carries the name of what someone is trying to do. Tool names therefore hold still while
the schema moves, and an agent can work usefully in Docket without knowing its data model.

## Tools

<AccordionGroup>
  <Accordion title="Reading: 5 tools" defaultOpen>
    | Tool | Does |
    | --- | --- |
    | `workspaces` | Lists the workspaces you belong to. Usually the first call. |
    | `find` | Ranked relevance search across the whole workspace. |
    | `list_work` | Enumerates live rows by exact criteria. |
    | `get` | Reads one or more entities in full, by ID or by name. |
    | `brief` | What needs me today. |

    **`find` and `list_work` answer different questions.**

    `find` runs ranked search over tasks, projects, programs, initiatives, cycles, milestones,
    comments, updates, attachments, calendar events, agent sessions, teams, members, and labels. It
    reads the same permission-filtered index the web app uses, so results are trimmed to what the
    caller may actually see. The index trails writes by a moment.

    `list_work` enumerates live rows by exact criteria: team, project, assignee, delegate, state,
    priority, label, cycle, due window, blocked-ness, and unfiled work in the triage queue. Pass a
    filter the chosen entity has no column for and the call **fails, naming the filters that entity
    does support**.

    `get` reads entities in full: a task with its dependencies and subtasks, a project with its
    milestones and latest update. References you cannot see come back in `missing`, and the rest of
    the batch still succeeds.
  </Accordion>

  <Accordion title="Writing: 9 tools">
    | Tool | Does |
    | --- | --- |
    | `capture` | A sentence becomes a task. |
    | `organize` | A whole plan in one call, reconciled so a re-run creates no duplicates. |
    | `update` | Changes work by describing which work. |
    | `comment` | Adds threaded discussion. |
    | `report_status` | Posts an update, driving the item's health. |
    | `link` | Links Docket work to Docket work. |
    | `archive` | Archives work. |
    | `plan_day` | Builds a day's plan. |
    | `undo` | Reverses a previous change set. |

    **Every write records an undoable change set**, and `undo` reverses it in one call. An agent
    can safely apply a batch, because a single call takes the batch back.

    Reach for `organize` when you are applying a plan instead of a single edit. It reconciles
    against what already exists, so running it twice produces one result.
  </Accordion>

  <Accordion title="Time and reflection: 2 tools">
    | Tool | Does |
    | --- | --- |
    | `track` | Records time against work. See [Time](/guides/daily/time). |
    | `retrospect` | Produces a retrospective over a period of work. |
  </Accordion>

  <Accordion title="Repeating work and processes: 3 tools">
    | Tool | Does |
    | --- | --- |
    | `define_process` | Defines a repeatable process. |
    | `schedule_process` | Puts a defined process on a schedule. |
    | `repeat_task` | Makes a task recur. |

    All three need `work:write`.
  </Accordion>

  <Accordion title="Agents, sessions, and connectors: 6 tools">
    | Tool | Does |
    | --- | --- |
    | `run_agent` | Triggers an agent session. |
    | `manage_session` | Manages a running session: approve, reject, steer. |
    | `link_external` | Links an external item from GitHub or Linear onto Docket work. |
    | `acknowledge_directive` | Acknowledges a scheduling directive. |
    | `pause_athena_assignment_trigger` | Pauses one trigger on your personal Athena assignment. |
    | `remove_athena_assignment_trigger` | Removes one trigger on your personal Athena assignment. |
  </Accordion>
</AccordionGroup>

### Scopes per tool

| Scope | Covers |
| --- | --- |
| `work:read` | `workspaces`, `find`, `list_work`, `get`, `brief`, and every resource read |
| `work:write` | `capture`, `organize`, `update`, `comment`, `report_status`, `link`, `archive`, `plan_day`, `undo`, `track`, `retrospect`, `acknowledge_directive`, `define_process`, `schedule_process`, `repeat_task` |
| `agents:run` | `run_agent`, `manage_session`, `pause_athena_assignment_trigger`, `remove_athena_assignment_trigger` |
| `connectors:link` | `link_external` |

See [Authentication](/developers/authentication#scopes) for how clients request scopes and step
them up.

## Resources

Reads are also modelled as resources. Every one is permission-gated and hides existence: an item
you cannot see looks the same as one that does not exist.

### Static

| URI | Contents |
| --- | --- |
| `docket://orgs` | Every workspace you belong to |
| `docket://hub/today` | Your daily plan |
| `docket://hub/inbox` | What needs a response |
| `docket://hub/directive` | The current scheduling directive |
| `docket://hub/portfolio` | Every workspace's programs and projects |

### Templated

```
docket://{org}/{type}/{id}
```

Where `type` is one of `task`, `project`, `program`, `initiative`, `cycle`, `team`, `update`,
`comment`, `session`, `agent`, `view`, or `org`.

### Subscriptions

Resources support `resources/subscribe`. A subscribed client holding the `GET /mcp` stream open
gets `notifications/resources/updated` when something changes. Delivery is best-effort and never
replayed, so treat a notification as a prompt to re-read the resource.

## Prompts

Three prompts bootstrap an agent with workspace context.

| Prompt | Purpose |
| --- | --- |
| `docket_system` | The Docket system prompt |
| `task_brief` | A brief on one task |
| `standup` | A standup summary |

## Widgets

The server also serves UI resources under `ui://docket/*` for hosts that render MCP Apps, covering
work lists, entities, tasks, projects, programs, initiatives, cycles, teams, updates, comments,
sessions, agents, views, organizations, plans, and change reports.

Hosts without MCP App support ignore these and get the structured results as normal.

## Server capabilities

The server advertises `tools.listChanged`, `resources.subscribe`, `resources.listChanged`,
`prompts.listChanged`, `completions`, and `logging`. Experimental MCP task support is available
behind a deployment flag.

<Note>
  `tools/list` reflects **your** grants. Two people connecting the same client can legitimately see
  different tool lists. A grant change fires `notifications/tools/list_changed` immediately, with
  no reconnect needed.
</Note>
