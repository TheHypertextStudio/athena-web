Docket returns only the tools that the caller's current scopes and grants allow. Tool availability
can change after consent or grant changes, so handle `notifications/tools/list_changed`.

## Tools

The work and planning tools are `workspaces`, `find`, `list_work`, `brief`, `capture`, `organize`,
`update`, `milestones`, `comment`, `report_status`, `link`, `archive`, `plan_day`, `undo`,
`retrospect`, `define_process`, `schedule_process`, `repeat_task`, `define_labels`,
`define_template`, `list_templates`, `plan_start`, `plan_read`, `plan_draft`, `plan_commit`, and `track`.

The agent, session, connector, and directive tools are `run_agent`, `manage_session`,
`link_external`, `acknowledge_directive`, `pause_athena_assignment_trigger`, and
`remove_athena_assignment_trigger`.

`get` is the compatibility generic entity read. Prefer the semantic readers when a client knows the
entity type: `get_tasks`, `get_projects`, `get_programs`, `get_initiatives`, `get_cycles`,
`get_teams`, `get_updates`, `get_comments`, `get_sessions`, `get_agents`, `get_views`, and
`get_organizations`.

`review_work_destination` reviews a proposed work destination before writing. It does not create
or move work on its own.

### Writing

    | Tool | Does |
    | --- | --- |
    | `capture` | Creates a task from a sentence. |
    | `organize` | Applies a whole plan in one call, milestones included. Re-runs create no duplicates. |
    | `update` | Changes work you describe in words, including which milestone a task is on. |
    | `milestones` | Lists, creates, updates, and deletes a project's milestones. |
    | `comment` | Adds threaded discussion. |
    | `report_status` | Posts an update. The verdict you set becomes the item's health. |
    | `link` | Links Docket work to Docket work. |
    | `archive` | Archives work. |
    | `plan_day` | Creates the day's plan. |
    | `undo` | Reverses a change set. |

    **Every write records an undoable change set.** Call `undo` once and Docket reverses forty
    edits.

### Time and reflection

    | Tool | Does |
    | --- | --- |
    | `track` | Records time against work. See [Time](/guides/daily/time). |
    | `retrospect` | Returns a retrospective for a period. |

### Repeating work and processes

    | Tool | Does |
    | --- | --- |
    | `define_process` | Defines a process. |
    | `schedule_process` | Schedules a process to run. |
    | `repeat_task` | Makes a task recur. |

### Create work from a template body

Agents writing tasks, projects, initiatives, or programs should generally look for a relevant
template before composing a description. Docket sends this instruction during MCP initialization,
in the system prompt, and in the creation tool descriptions.

Call `list_templates` with `orgId` and the matching `targetType`. Follow `nextCursor` when needed.
The full literal Markdown body is `payload.description`. The template's top-level `description`
only explains when to use it. Read the body, keep its headings and instructions, and fill its
sections with the work details. Do not replace it with an invented format or treat attaching an
ID as using the template.

For example, a Project template with `## Outcome`, `## Scope`, and `## Evidence` should produce a
project description with those sections filled in. Use the same rule for a Task, Initiative, or
Program template. If none fits, the person requests freeform work, or quick capture needs no
outline, proceed without one. Milestones, Cycles, and Teams have no work templates.

The creation paths accept the body in these places:

| Tool                      | How to use the template body                                                                                                                                                                          |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `capture`                 | Put the task title first, then the completed Markdown in `text`.                                                                                                                                      |
| `organize`                | Put the completed Markdown in each item's `description`.                                                                                                                                              |
| `plan_start`, `plan_read` | Read each template's `body`; both return the full Markdown.                                                                                                                                           |
| `plan_draft`              | Add a node, apply `{op: "apply_template", ref, templateId}` before drafting its body, then use `set_fields` to fill its sections.                                                                     |
| `repeat_task`             | Pass a visible task template as `template` and the completed Markdown as `recurringTask.task.description`. Explicit body and properties win; omitted fields use the saved body, priority, and labels. |

`apply_template` copies missing fields. It does not write the content of the sections, replace an
existing body, or create child work. Setting a node's `templateId` alone copies nothing. Templates
may carry secondary property defaults; preserve explicit values. An explicit empty label list
keeps a repeating task unlabelled, deleted default labels are dropped, and a team template must
match the repeating task's team. Personal and team templates remain permission-filtered.

`list_templates` needs `work:read` and workspace `view` access. It initializes shipped defaults
on the first template read, following the same rule as the template picker. `define_template`
authors reusable bodies. `define_process` and `schedule_process` separately define multi-step
recurring work and its schedule.

### Labels and templates

    | Tool | Does |
    | --- | --- |
    | `define_labels` | Creates or edits label groups and labels in one call. Entries match by name, so a re-run changes nothing. |
    | `list_templates` | Returns visible templates with literal Markdown bodies and property defaults. |
    | `define_template` | Creates or edits one task, project, initiative, or program template. |

    Put labels on work with `update`: `set.labels` takes `add` and `remove`, or `replace` on its
    own. A label limited to one team only goes on that team's work, and anything else is reported
    as `label_out_of_scope`.

    Creating a label or a template needs `contribute` access. Renaming, recoloring, regrouping, or
    rescoping a label, and any change to a label group, needs `manage` access. An entry the caller
    may not write comes back in `skipped` while the rest of the call applies. Undoing a created
    label or group deletes it only while nothing uses it, and reports it as `in_use` otherwise.
    `define_labels` and `define_template` do not delete or merge labels and templates. Use the
    settings pages for that.

### Agents, sessions, and connectors

    | Tool | Does |
    | --- | --- |
    | `run_agent` | Starts an agent session. |
    | `manage_session` | Approves, rejects, or redirects a running session. |
    | `link_external` | Links a GitHub or Linear item onto Docket work. |
    | `acknowledge_directive` | Acknowledges a directive. |
    | `pause_athena_assignment_trigger` | Pauses a trigger on your Athena assignment. |
    | `remove_athena_assignment_trigger` | Removes a trigger on your Athena assignment. |
    | `review_work_destination` | Reviews whether a normalized web destination supports one task, with at most one follow-up question. |

### Scopes per tool

| Scope             | Covers                                                                                                                                                                                                                                                                                         |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `work:read`       | `workspaces`, `find`, `list_work`, `list_templates`, `get`, `brief`, `milestones` with `list`, and every resource read                                                                                                                                                                         |
| `work:write`      | `capture`, `organize`, `update`, `milestones` with `create`, `update`, or `delete`, `comment`, `report_status`, `link`, `archive`, `plan_day`, `undo`, `track`, `retrospect`, `acknowledge_directive`, `define_process`, `schedule_process`, `repeat_task`, `define_labels`, `define_template` |
| `agents:run`      | `run_agent`, `manage_session`, `pause_athena_assignment_trigger`, `remove_athena_assignment_trigger`, `review_work_destination`                                                                                                                                                                |
| `connectors:link` | `link_external`                                                                                                                                                                                                                                                                                |

See [Authentication](/developers/authentication#request-the-smallest-scope) for requesting and stepping up scopes.

`work:read` gates reads. `work:write` gates work mutations and time tracking. `agents:run` gates
agent sessions and Athena assignment controls. `connectors:link` gates external linking.
`offline_access` only allows token refresh. Every call still checks the person's current Docket
grant.

## Resources

Use these caller-scoped resources for discovery and Hub views:

| URI                        | Contents                                                                      |
| -------------------------- | ----------------------------------------------------------------------------- |
| `docket://orgs`            | Every workspace you belong to                                                 |
| `docket://hub/today`       | Your daily plan                                                               |
| `docket://hub/inbox`       | What needs a response                                                         |
| `docket://hub/directive`   | The current scheduling directive                                              |
| `docket://hub/portfolio`   | Every workspace's programs and projects                                       |
| `docket://hub/active-work` | Your current running or paused timer and its permission-filtered task context |

Read one entity through:

```text
docket://{org}/{type}/{id}
```

`type` is `task`, `project`, `program`, `initiative`, `cycle`, `team`, `update`, `comment`,
`session`, `agent`, `view`, or `org`. Docket returns an unreadable resource as not found.

MCP Apps clients can also render `ui://docket/*` resources. Other clients receive structured tool
and resource results. Results from the `get_*` tools and `update` can include
`_meta["docket/render"]`, a display model the app draws from. Clients that do not render apps can
ignore it.

## Prompts and notifications

The server registers `docket_system`, `task_brief`, and `standup` prompts. It supports resource
subscriptions and emits `notifications/resources/updated` as a best-effort signal. Re-read the
resource after the signal because Docket does not replay a notification stream.

The server also advertises `resources.listChanged`, `prompts.listChanged`, completions, and logging.
Experimental MCP task support depends on the deployment configuration and is not a public REST API
capability.
