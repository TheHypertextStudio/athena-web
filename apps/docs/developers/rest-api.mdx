## Authentication

Bearer token on every request:

```http
Authorization: Bearer <token>
```

**Every endpoint requires one except `GET /v1/config`**, the public bootstrap config. A global gate
applies authentication ahead of the handlers, so no route becomes public by accident.

See [Authentication](/developers/authentication) for how to get a token.

## Conventions

<AccordionGroup>
  <Accordion title="Identifiers are ULIDs" defaultOpen>
    26 Crockford base-32 characters, matching `^[0-9A-HJKMNP-TV-Z]{26}$`.

    Each entity type carries its own branded ID, so IDs are **not interchangeable across
    resources**. A `TaskId` fails where a `ProjectId` belongs. Treat IDs as opaque and never parse
    them.
  </Accordion>
  <Accordion title="Pagination is keyset, never offset">
    Pass `cursor` and `limit`; read `nextCursor` from the response. It is `null` on the last page.

    ```http
    GET /v1/orgs/{orgId}/tasks?limit=50&cursor=<opaque>
    ```
  </Accordion>
  <Accordion title="Errors are RFC 9457 problem documents">
    `application/problem+json`, carrying a stable machine-readable `code`, an HTTP `status`, and
    per-field `fieldErrors` on validation failures.

    **Branch on `code`.** See [Errors](/developers/errors).
  </Accordion>
  <Accordion title="Creates accept an Idempotency-Key">
    ```http
    Idempotency-Key: <your-unique-key>
    ```

    A retried request never duplicates a resource.
  </Accordion>
  <Accordion title="Request and response bodies share one schema">
    Docket validates both against the same schemas the reference renders, so the documented shape
    is the runtime shape. A response that does not match its schema is a bug.
  </Accordion>
</AccordionGroup>

## Permissions

Docket always applies two layers.

**Membership.** Every `/v1/orgs/{orgId}/*` route requires an active Actor in that workspace.
Non-members receive **404** in place of 403. Docket hides existence, so you cannot learn that a
workspace or resource exists unless you may see it.

**Capability.** Mutations require a capability on the ladder:

```
view  <  comment  <  contribute  <  assign  <  manage
```

Reassigning work needs `assign`. Commenting needs `comment`. Administrative changes need `manage`.
Read endpoints apply a visibility and grant predicate inside the query, so every row you receive is
one you may see, and client-side filtering is unnecessary.

Agents pass the identical checks. An agent is an Actor with explicit grants, and the
[approval gate](/guides/athena/proposals-and-approvals) applies on top.

## Cross-workspace surfaces

Some surfaces span tenants by design: the Hub (`/hub/today`, `/portfolio`, `/search`, `/inbox`,
`/activity`), notifications, and the personal daily plan.

Docket fans these out as **one permission-scoped query per membership** and merges the results in
application code. No SQL join crosses tenants. Every item carries its own `organizationId` and runs
through that workspace's visibility predicate individually, so the result is a union of
per-workspace permission decisions.

## Live updates

`GET /v1/stream/sse` is a server-sent event stream of `stream-event` frames, with a ping every 25
seconds. Typed paginated fallbacks exist at `/v1/hub/stream` and `/v1/orgs/{orgId}/stream` for
clients that cannot hold a connection open.

<Warning>
  Docket sends **no outbound webhooks**. It receives them from connected providers. To react to
  changes, poll a stream endpoint or subscribe over
  [MCP](/developers/mcp-tools-and-resources#subscriptions).
</Warning>

## REST or MCP?

The same operations reach agents over the [MCP server](/developers/connect-an-agent-mcp), which
calls the identical service layer beneath the same permission engine.

| Choose | When |
| --- | --- |
| REST | You know exactly which record you want and which fields to set. |
| MCP | Your caller describes intent. MCP tools accept names anywhere IDs are accepted, and `organize` applies a whole plan in one reconciled call. |
