Initiatives and Programs both sit above a Project, and they do different jobs.

<CardGroup cols={2}>
  <Card title="Program" icon="rotate">
    An **ongoing area of operations**. It holds real work and usually runs on.
    "Customer Support." "After-School Program." "Donor relations."
  </Card>
  <Card title="Initiative" icon="flag">
    A **strategic theme**. It holds no work of its own and gathers other things under one heading.
    "Grow revenue." "Expand to a second city."
  </Card>
</CardGroup>

## Program: continuous work

A Program is the continuous counterpart to the bounded [Project](/guides/concepts/projects).

Real organizations run work that keeps going after each deliverable inside it lands. Support
tickets keep arriving. Books keep needing to be current. A tutoring program runs every term. A
Project ends and an Initiative holds no work, so a Program holds work of this kind.

**A Program contains work directly.** It can hold Projects, such as the bounded push "Fall term
enrolment" inside the continuous "After-School Program". It can also hold Tasks with no project at
all, which is the usual shape of ongoing and recurring work.

You read a Program through its **health and flow** instead of a progress bar. A percentage
complete means very little for work designed to keep going.

### Programs can end

Most run on indefinitely. A real after-school program can still be wound down at the end of its
last term, and an operations function can be retired.

The seeded program statuses are `Proposed · Active · Paused · Completed · Archived`, where
`Archived` means retired and kept for history. Statuses are workspace-defined, so a workspace whose
programs only ever end by being archived can delete `Completed` from its program set. See
[Labels and statuses](/guides/concepts/labels-and-statuses).

## Initiative: a theme that holds no work

An Initiative names a strategic theme. "Grow revenue" is the reason several separate efforts
belong together, and nobody works on it directly.

**Initiatives contain no work themselves.** Programs and Projects *associate* with them, and the
relationship is many-to-many, because themes cut across structure. One project can serve both
"Grow revenue" and "Expand to a second city", and neither theme owns it.

An initiative reports rolled-up health and the mix of what sits under it.

### Nesting

Workspaces can arrange Initiatives into a shallow hierarchy. The maximum depth defaults to two
total levels and is configurable in **Settings → Work structure**.

Hierarchy links are contextual references. One may point at an Initiative in another workspace.
The link records a relationship and grants no access to what it points at.

## Containment and association, side by side

Docket keeps two kinds of relationship apart.

| | Containment | Association |
| --- | --- | --- |
| **Means** | A hard parent → child. The child cannot exist without the parent. | A soft, optional link. Either side can exist alone. |
| **Examples** | A workspace contains its work. A project contains its tasks. | An initiative themes a project. A cycle schedules a task. A task blocks a task. |
| **Cardinality** | One parent. | Many-to-many. |

Because the two stay separate, one task can be themed by two initiatives, scheduled into a cycle,
and blocked by something in a different project, all at once.

## Choosing between them

| The work | The shape |
| --- | --- |
| Has an outcome and a finish line | [Project](/guides/concepts/projects) |
| Keeps going, and holds real work | Program |
| Is a reason several efforts belong together | Initiative |
| Is one thing a person does | [Task](/guides/concepts/tasks) |

<Tip>
  If you cannot decide between a Program and an Initiative, ask whether tasks would ever sit
  directly inside it. If yes, it is a Program.
</Tip>
