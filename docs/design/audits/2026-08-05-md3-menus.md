# Menu compliance audit

Read this if you are about to change a menu's geometry or colour. It records what the M3
Expressive vertical menu spec requires, what Docket renders, where the two deliberately differ,
and what has not been checked. The token table itself lives in
[`docs/design/references/md3-menus.md`](../references/md3-menus.md) against a pinned source
revision; this file does not restate it.

## What was measured

Two passes, because they answer different questions.

The **live pass** ran against the running app on an authenticated session and read computed
styles off real menus. It is the authority for "does the product render this", and its output is
[`screenshots/2026-08-05-md3-menus/measurements.json`](screenshots/2026-08-05-md3-menus/measurements.json).
Container radius is 16px with 4px padding and the level2 shadow pair at z-index 120; rows are
44px tall with 16px leading space, 12px between-space, 4px radius, `label-large` at 14/20/500/0.1,
and 20px icons in `on-surface-variant`. Light and dark agree.

The **shape pass** drove the class builders directly against the compiled stylesheet, forced
`:hover` through CDP, and read back the radius of every hovered row across six configurations —
both colour mappings, both section treatments, a menu led by a label, and a menu whose rows sit
inside a semantic group. Its output is
[`hover-shape-findings.json`](screenshots/2026-08-05-md3-menus/hover-shape-findings.json).

## Concentric shape

A hovered row's state layer takes the row's own radius, so the hover state is where a wrong
corner becomes visible. The rule the implementation follows is geometric rather than positional:
a row takes its nearest **painted** ancestor's radius less that ancestor's padding on whichever
edges it physically touches, and 4dp everywhere else.

| Where the row sits                  | Painted ancestor   | Its radius | Less 4dp padding | Row radius  |
| ----------------------------------- | ------------------ | ---------- | ---------------- | ----------- |
| Top of a divider menu               | container          | 16dp       | 12dp             | `12,12,4,4` |
| Bottom of a divider menu            | container          | 16dp       | 12dp             | `4,4,12,12` |
| Interior of any menu                | container or group | —          | —                | `4,4,4,4`   |
| Top of a gapped menu's first block  | group              | 16dp       | 12dp             | `12,12,4,4` |
| Either side of a gapped menu's seam | group              | 8dp        | 4dp              | `4,4,4,4`   |
| Under a section label               | container          | 16dp       | —                | `4,4,4,4`   |

The seam is the case worth understanding. A group's 8dp seam corner less the same 4dp inset is
exactly 4dp, which is the row's own `menu-item.shape`, so a seam row needs no override at all —
the arithmetic lands on the value it already had. That is why the only difference between the
`divider` and `gap` treatments is the gap itself.

The label row is the other case that surprises people. `Under a section label` keeps 4dp because
the label, not the row, is what touches the container's top edge. The rule is about geometry, so
it sees that without anyone encoding it.

All 22 hovered rows satisfy the rule. Screenshots:
[edges](screenshots/menu-hover-edges-light.png) and
[interior](screenshots/menu-hover-interior-light.png), with dark variants beside them.

## Mobile width

`xl` (352px) is the widest step and the only one that could exceed a 390px viewport. At 390x844
it measures 352px with its right edge at 364px, the context menu measures 224px, and the document
does not scroll sideways —
[`mobile-report.json`](screenshots/2026-08-05-md3-menus/mobile-report.json), captured in

## Deliberate deviations

**The section gap is 4dp, not the token's 2dp.** `md.comp.menus.gap` is 2dp, and sampling the
spec figure confirms its seam really is that. What makes 2dp read there is the lower block's drop
shadow darkening the page behind it. Docket's `level2` is lighter, so at 2dp the seam disappeared;
it takes the next measurement step up.

**Vibrant menus do not use `outline-variant` for their divider.** Neither expressive colour set
defines a divider token, so the role comes from the Divider component. That component's
`outline-variant` is drawn from the neutral-variant palette and assumes a neutral surface; on
`tertiary-container` it is a grey hairline belonging to no tonal family, and in dark it barely
resolves. Vibrant uses `on-tertiary-container` held to a hairline's weight instead.

**The focus indicator's colour is not the spec's `secondary`.** Docket's `--secondary` is the
shadcn near-white button role, not an M3 tonal secondary, and the M3 role is absent from the
token set. Menus take a correct 3dp/-3dp indicator under `--ring`. The name collision is a
system-level problem and is not a menu decision.

## Not verified

`CORE-06` — no popup may render flush against a viewport edge — is still recorded as `fail` in
the compliance ledger on evidence from 2026-08-02, when the Display dropdown measured a 0px
bottom gap. Every menu, popover, tooltip, and hover card now passes
`collisionPadding={OVERLAY_COLLISION_PADDING}` (12dp) and caps at
`--radix-*-content-available-height`, which Radix computes with that inset already subtracted, so
the defect is very likely gone. **This has not been re-measured on the running app.** Confirming
it needs the Projects → Timeline lens at 1440x900 with the Display dropdown open, and an attempt
on 2026-08-07 failed because the machine sat at a load average of 56–75 and Turbopack did not
finish compiling `/sign-up` in fifteen minutes. Re-run it on a quiet machine before treating
`CORE-06` as closed.
