# Writing Docket documentation

Write for the person completing a task: state prerequisites, give steps in order, explain the
expected result, and offer recovery where failure is possible. Use Docket's actual object and
action names. Keep planning guides, developer reference, and dated changelog entries in their
existing navigation groups.

## Choose and write a page

An overview explains purpose and the next useful task. A quickstart follows one complete path to
a result. A guide covers one task and its recovery. A reference describes exact inputs,
authorization, outputs, and errors. A changelog describes observable changes and required action.

Begin each MDX page with a useful frontmatter title and a description of at least 30 characters.
Use sentence case headings, descriptive links, and meaningful image/video alternative text.
Use Mintlify's native `Steps`/`Step`, `Note`/`Warning`, `Tabs`/`Tab`, and `CodeGroup` where they help.
Keep ordinary explanation in Markdown. Do not introduce a separate component, search, or API
reference system.

Use extensionless local links such as `/guides/daily/tasks`. Keep published paths and heading
anchors stable. If a page moves, add a redirect in `docs.site.json` and update its links in the
same change. Add every public page to the existing navigation and regenerate `docs.json`.
Preserve existing redirect sources unless a separately reviewed migration retires them.

Code samples name their language, include the complete command/request, identify values the
reader replaces, and explain success. Use example credentials, never live secrets or personal
customer data. REST endpoint details remain generated by the API's Scalar `/v1/docs` surface;
link there from `developers/rest-api.mdx` rather than duplicating the OpenAPI document.

## Review and publish

1. Edit MDX/assets and product-owned `docs.site.json`.
2. Run `pnpm docs:config` and review the generated diff with the content.
3. Run `pnpm docs:check`. It includes native Mintlify validation, links, anchors, redirects,
   snippets, accessibility, navigation/frontmatter/local-link checks, and Docket's vocabulary,
   OAuth, and MCP coverage policy. Do not weaken these gates to land new content.
4. Run `pnpm docs:dev` and inspect changed pages at narrow and wide widths, using the keyboard.
   Check examples, code overflow, navigation, search, logos, links, and image descriptions.
5. Follow this repository's direct linear-history workflow after local review and required checks.
   Docket does not use pull requests. A docs-only source change does not authorize provider or
   application changes.
6. Record the reviewed source SHA and actual Mintlify result. Verify the published `/docs` prefix,
   assets, redirects, anchors, search, canonical URLs, and Scalar link independently of the
   application release. Use [the operating reference](docs-operations.md).

Hosted preview entitlement is currently unavailable. Use the pinned local preview; do not start
another trial or create an admin API key to review a page. Local checks do not establish that the
provider published the reviewed source.
