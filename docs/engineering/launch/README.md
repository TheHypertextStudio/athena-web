# The launch record

The launch record answers one question, honestly, at any moment: **which of the launch plan's
requirements are actually done, who did them, and what evidence backs the claim.**

**One tool writes the ledger: `pnpm exec tsx scripts/launch-record.ts`.** It reads the audited
baseline and every slice file, and writes two generated artifacts:

- `docs/engineering/launch/launch-record.json` — the record. `owner`, `claim`, `state`,
  `verifiedBy`, and `verificationArtifacts` are **derived from the slice files** on every run;
  only genuinely human-authored fields (`evidence`, `worklogAnchor`, `blockedReason`, `questions`,
  `externalSystems`) survive regeneration untouched.
- `docs/engineering/launch/launch-checklist.md` — a readable rendering of it. Generated. Never
  edited by hand.

Other workers keep their own notes in this directory — `obstacle-log.md`, `external-systems.md`,
`questions.md`, `verification-log.md`, `production-verification.md`, and `evidence/`. Those are
narrative; the two files above are the requirement-by-requirement ledger, and `slices/*.md` is
where the claims they are built from live.

> **There used to be two ledgers, and that was the defect this directory is now organized against.**
> Two lanes independently built a launch record: a JSON-backed one generated by
> `scripts/launch-compliance-record.ts`, and a slice reconciler that wrote a separate
> `checklist.md`. Each was internally consistent, so each had its own green test and neither looked
> broken — yet they disagreed, because `GEN-07` and `GEN-23` were graded `pass` by
> `slices/security-and-domains.md` and left `not-started` in the record. Two ledgers meant two
> answers to "how much of the launch is done?", and a reader believed whichever they opened first.
> The second generator and `checklist.md` are gone; the state that used to be typed into the record
> by hand is derived, so it cannot be edited into disagreement with the slices. What remains of the
> old bracket is a regression guard: `sliceClaimViolations` in `launch-record-schema.ts` holds every
> entry between `MIN_STATE_FOR_CLAIMED_REQUIREMENT` and `MAX_STATE_FOR_SLICE_OUTCOME` and checks
> `owner` against the claiming slices, so a future hand-edit or a bug in the derivation is caught
> rather than published. See `slices/launch-governance.md` § "Cross-worker conflict, recorded".

# The slice record

The second half of this directory: **per-worker slice files, and the reconciler that maps them onto
the audited baseline.** This is what `GEN-01`, `GEN-09`, and `MISS-07` are graded on.

| File                   | What it is                                                                    | Graded by      |
| ---------------------- | ----------------------------------------------------------------------------- | -------------- |
| `launch-checklist.md`  | **Generated.** One row per requirement: its owner, slice claim, graded state. | GEN-01         |
| `obstacle-log.md`      | Every obstacle actually hit, with the session/command used to get past it.    | GEN-03, GEN-04 |
| `external-systems.md`  | Per external system: a captured authenticated call, or ≥3 failed workarounds. | GEN-05         |
| `questions.md`         | Every question asked of the author, in the required three-field form.         | GEN-08         |
| `verification-log.md`  | Per slice: the verification subagent, and an artifact **it** produced.        | GEN-09         |
| `slices/<slice-id>.md` | One per worker. The canonical record of what that worker shipped.             | MISS-07        |

## Why slice files are the canonical record, not commits

MISS-07's acceptance asks for each slice to be mapped to a landed commit. This launch is delivered as
a **working tree on `claude/docket-production-launch-ebe2d9`**, not as a series of landed commits —
the workers building it are explicitly forbidden from committing, because several of them edit the
same tree concurrently and an interleaved commit would attribute one worker's files to another.

The resolution, stated here so nothing downstream has to infer it:

> **A slice file is the canonical record of shipped work.** `slices/<slice-id>.md` names the branch,
> the requirement ids the slice closes, the files it changed, and the validation output. When the
> branch is committed, each slice file is the commit message's source material and the mapping from
> requirement id to commit is mechanical.

The half of MISS-07 that does not depend on commits is enforced exactly as written:

```sh
$ git rev-list --merges --count origin/main..HEAD
0
```

## The slice-file contract

A slice file is **Markdown, named `slices/<slice-id>.md`**. That is not a stylistic preference:
`loadSlices` in `scripts/launch-record.ts` filters on `.endsWith('.md')`, so a slice recorded in any
other format is not read, not reconciled, and not in the ledger — while looking, to whoever
wrote it, exactly like a filed record. That happened once: `security-and-domains` was briefed on a
`slices/<slug>.json` shape and filed a 50 KB JSON record that no tool ever loaded. It has since been
folded into its `.md` and deleted. If a future contract wants JSON, teach `loadSlices` to read it
first.

Every slice file starts with a YAML frontmatter block in exactly this shape. `scripts/launch-record.ts`
parses it with a strict reader — anything outside this shape is a hard parse error, not a warning.

```markdown
---
slice: ci-gating
branch: claude/docket-production-launch-ebe2d9
requirementIds: [GEN-02, GEN-06, SCR-15]
outcomes:
  GEN-02: partial
  GEN-06: pass
  SCR-15: pass
filesChanged:
  - .github/workflows/ci.yml
verifier: production-verification-agent
verifierArtifacts:
  - docs/engineering/launch/evidence/production/2026-08-02-secret-sweep.txt
verification: 'pnpm exec vitest run repo-tests/ci — 14 passed'
---

## GEN-02 — <requirement title>

**Acceptance:** <quote the acceptance clause>
**What was built:** …
**Evidence:** <exact command + its output, or a path to a captured artifact>
**Residual gap (if outcome is not `pass`):** <what is still missing and who must do it>
```

Rules the parser enforces, and why they are enforced rather than trusted:

- `outcomes` uses the same five values as the audit baseline:
  `pass | partial | fail | not-built | unverifiable`. A sixth value (`deferred`, `TODO`, `blocked`)
  is rejected — those are the words GEN-01 counts, and they have no place in a record whose job is
  to reach zero of them.
- Every id in `requirementIds` must have an `outcomes` entry, and `outcomes` may not name an id the
  slice did not list. Both directions are checked, because either gap is how a requirement silently
  goes unowned.
- A requirement id appears in exactly **one** slice file. The single deliberate exception is
  `GEN-06`, whose acceptance has two independent clauses split across two slices; it is allowlisted
  by id in `scripts/launch-record.ts` with the reason inline. When two slices claim it, the
  **weakest** outcome wins, since both clauses must hold before it can read `pass`.
- **`verifier` must not name the slice itself.** Casing, separators, and a trailing
  `-verifier` / `-verification` / `-verify` / `-reviewer` / `-review` / `-checker` are stripped
  before comparing, and containment counts — so a `ci-gating` slice cannot verify itself as
  `ci_gating_verifier`. This is GEN-09's independence clause, and it is a parse error.
- **`verifierArtifacts` must be non-empty, must exist on disk, and at least one must sit under a
  verifier-owned evidence root** (`docs/engineering/launch/evidence/` or
  `docs/design/audits/screenshots/`). Authorship is not recoverable from a path, so the repository
  encodes it by convention: implementers write source and docs, verifiers write captured output. A
  slice citing only its own source files has cited nothing.

These two fields are what let a requirement reach `closed` at all. `stateForClaim` in
`scripts/launch-record.ts` holds a `pass` claim at `in-progress` until its slice's verification
holds, and the CLI prints that gap as `awaiting-verification=N` on every run. Nobody can close a
requirement by editing the record, because the record's `state` is derived, not written.

What the parser cannot enforce, and is on the author: **never write `pass` for evidence you did not
personally produce.** A harness that exists but was never run is `partial`. Evidence is a command
plus its real output, or a file that exists on disk.

## Regenerating the ledger

```sh
pnpm launch:record
```

Reads the baseline, parses every slice file, reconciles them, and rewrites **both**
`launch-record.json` and `launch-checklist.md` (Prettier-formatted, so `pnpm format:check` stays
green). Running it twice produces byte-identical output, so a dirty `git status` after a second run
means the ledger genuinely changed.

The headline it prints is the launch's one status line:

```
requirements=399 closed=12 open=387 awaiting-verification=0 slices=4 sign-off=withheld (387 gate violations)
```

`awaiting-verification` is the count of requirements a slice claims `pass` that no verifier has
confirmed. It is printed because it is exactly the quantity the two old ledgers disagreed about.

### The two modes

**Structural (default).** Every slice file parses; no requirement is claimed by two slices outside
the GEN-06 allowlist; no slice claims an id the baseline does not define. Exits non-zero on any of
those. **This must pass on every commit of the launch branch** — a failure means two workers think
they own the same requirement.

**Sign-off (`--sign-off`).** Additionally requires that _every_ baseline requirement is claimed by
exactly one slice and closed `pass`.

```sh
pnpm exec tsx scripts/launch-record.ts --sign-off
```

This is GEN-01's gate. It exits non-zero and prints every offending id with its severity and reason.
**It is expected to fail today.** The gate counts a strict superset of GEN-01's four words —
unclaimed, plus every non-`pass` disposition — because a requirement recorded `fail` or `not-built`
is no more shipped than one recorded `partial`. Narrowing that predicate to manufacture a green
sign-off is the specific dishonesty GEN-01 exists to prevent.

### Tests

```sh
pnpm exec vitest run repo-tests/launch
```

`repo-tests/launch/launch-record.test.ts` covers the parser's rejection cases, the reconciler's unclaimed
and doubly-claimed detection, the GEN-06 allowlist, and asserts against the **real** current data
that the committed checklist holds every baseline id exactly once and that sign-off is not clean.

# The requirement ledger

The rest of this README covers `launch-record.json` and `launch-checklist.md` and the rules that
govern them.

## Where the requirement list comes from

`docs/engineering/launch-compliance.json` is the audit: 399 requirements pulled out of the launch
plan, each with a stable id (`GEN-01`, `SCR-22`, `MISS-07`, …), the sentence it came from, the bar
it is graded against, and a severity.

**That file is never hand-edited, and nothing in this repo writes to it.** It fixes the bar. The
launch record follows it — it cannot add an id the audit does not define, cannot drop one the audit
does define, and re-reads each requirement's area and severity every time it is regenerated. If the
audit is redone, regenerate; the record will pick up the changes and keep every note anyone has
written.

## Regenerating

Same one command as the slice ledger — they are the same tool: `pnpm launch:record`. See
"Regenerating the ledger" above. It is safe to run any time. `owner`, `claim`, `state`,
`verifiedBy`, and `verificationArtifacts` are **recomputed** from the slice files; `evidence`,
`worklogAnchor`, `blockedReason`, `questions`, `externalSystems`, and `signOff` are carried across
untouched.

Two policy tests keep the record honest. They run with the rest of the suite:

- `packages/test-utils/tests/launch-policies/launch-record.test.ts`
- `packages/test-utils/tests/launch-policies/worklog-and-history.test.ts`

## What each state means

| State         | Meaning                                                                    |
| ------------- | -------------------------------------------------------------------------- |
| `not-started` | Nobody has picked this up.                                                 |
| `in-progress` | Someone is working on it right now.                                        |
| `closed`      | Done and independently checked. Needs evidence, a verifier, and artifacts. |
| `blocked`     | Stopped by something outside this repo. Needs a permitted cause.           |

There is deliberately no "partial", no "deferred", and no "follow-up". The launch plan says every
requirement is finished before launch is declared, so the vocabulary refuses to express anything in
between. The tests also reject that language in free text, so it cannot sneak in through the
evidence field either.

## Closing a requirement

**You do not set `state` to `closed`.** `state` is derived; editing it in the JSON is overwritten on
the next regeneration. A requirement closes when, and only when, all of this is true:

1. Its slice file claims it `pass` in `outcomes`.
2. That slice names a `verifier` who is not the slice itself.
3. That slice's `verifierArtifacts` include at least one path that exists on disk under
   `docs/engineering/launch/evidence/` or `docs/design/audits/screenshots/`.

Then fill in the two fields that are genuinely yours to write:

- **`evidence`** — one factual sentence naming what shipped. At least 40 characters. Say what the
  artifact is, not that you feel good about it.
- **`worklogAnchor`** — the exact heading text of the `docs/WORKLOG.md` entry that records the
  slice. It must appear in the worklog exactly once, and each requirement id may sit under exactly
  one anchor. One slice may close several requirements; one requirement may not be claimed twice.

`verifiedBy` and `verificationArtifacts` still appear on each entry and are still checked by
`verificationViolations`, but they are copied from the claiming slice rather than typed here — a
value that can be typed in two places is a value that will eventually differ between them.

## Blocking a requirement

A `blocked` entry needs a `blockedReason` with a `cause` from this list and nothing else:

| Cause                         | When it applies                                         |
| ----------------------------- | ------------------------------------------------------- |
| `upstream-outage`             | Someone else's service is down.                         |
| `awaiting-third-party-review` | Someone outside the team has to approve or review.      |
| `requires-production-data`    | The answer only exists in data that does not yet exist. |

Everything else is not a blocker. In particular these are rejected outright, both as a `cause` and
as prose inside `detail`:

`documentation-unavailable`, `fetch-failed`, `paywalled-docs`, `js-only-docs`,
`missing-permission`, `missing-access`, `missing-credentials`, `could-not-sign-in`.

The reason is simple: the launch has complete access to the machine, its browsers, its command-line
tools, and its accounts. A documentation page that needs JavaScript is a page you open in a browser.
A login prompt is a login you complete. **An obstacle that is merely hard is not a blocker** — drive
the browser, use the CLI, sign in, and record what you did in the entry's `evidence`.

## Recording a question

The launch is meant to run to completion without stopping to ask. When a question genuinely has to
be asked, it goes in the record's `questions` array with three things:

```json
{
  "requirementId": "CAL-12",
  "candidateOutcomes": ["a modal over the current view", "a dedicated route"],
  "whyPlanCannotDecide": "The plan calls the surface \"focused\" without saying whether focus means a dialog or a route.",
  "askedAt": "2026-08-02T10:15:00.000Z"
}
```

A question is justified only when **two or more outcomes were each defensible** and **the plan text
selects neither**. A question with one candidate outcome was a decision you could have made. A
question with no explanation is not a question, it is an interruption. Asking without recording all
three fields fails the test suite — the point is not to forbid questions, it is to make the cost of
one visible.

## External systems

The record carries a row for each of the seven systems the launch touches: Google, Notion, Sunsama,
Cloudflare, Vercel, Lovelace Lattice, and Twilio. Each row is `authenticated` (with the call or
session captured in `evidence`), `not-required` (with `evidence` saying why the launch does not
touch it), or `attempting`.

`attempting` is honest, but it is not an end state. See the next section.

## Declaring launch

`signOff` starts `false`. Setting it to `true` is what declares launch, and doing so turns on the
full gate. At that point:

- **Every one of the 399 entries must be `closed`.** Not `not-started`, not `in-progress`, not
  `blocked`.
- **Every external system must have a working authenticated path** — `authenticated` with evidence,
  or `not-required`, or at least **three distinct workaround attempts** each recorded with what was
  tried and the failure output it produced.

The gate is a plain function, `signOffViolations`, in
`packages/test-utils/tests/launch-policies/launch-record-schema.ts`. You can run it any time to see
exactly what is standing between the record and a defensible launch — the checklist prints the count
in its summary table. It is not something that wakes up at the end; it is tested against fixtures
today so that it is known to work on the day it matters.
