A status is the answer to "how far along is this?" — `Todo`, `In Review`, `Shipped`. Docket used to
pick those words for you. A workspace now picks its own: it names its statuses, writes a line
explaining what each one means, decides how many it wants and what order they read in, and chooses
which one new work starts in. A grant-making nonprofit can run `Drafting → Submitted → Under
review → Awarded`, and a studio can run `Idea → Booked → Shot → Delivered`. Each is describing its
real process in its own words.

Every status a workspace invents declares one of **five categories**: `backlog`, `unstarted`,
`started`, `completed`, `canceled`. That much is Docket's, and it is the reason the rest can be
yours. The category is what a status glyph draws, what a board groups by, what a progress
percentage counts, what a connector maps a Linear or Jira state onto, and what tells the product
that a piece of work just finished. Two workspaces calling the same stage `Shipped` and `Awarded`
are both saying `completed`, so their numbers, their icons, and their integrations all still line
up. `Under review` and `Awaiting signature` can both be `started` — several statuses may share a
category, which is exactly how a workspace adds detail without inventing new physics.

Four kinds of work carry a status set: **Task, Project, Program, Initiative**. Each gets its own
set, because "how far along is this task" and "how far along is this program" are different
questions with different answers.

## The model

One status is `{ key, name, description, category, position, isDefault }`, declared in
`packages/types/src/work-status.ts` and stored in `work_status`
(`packages/db/src/schema/work-status.ts`).

| Field         | What it is                                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `key`         | Stable identifier within the set, generated by the server from the name at creation and **immutable** thereafter.           |
| `name`        | What people see on rows, pickers, and group headers. Up to 60 characters, non-blank once trimmed. Renaming moves only this. |
| `description` | What the status means, shown when someone is choosing between two of them. Up to 280 characters, clearable.                 |
| `category`    | Which of the five the status behaves as.                                                                                    |
| `position`    | Sort order **among the statuses sharing its category**, ascending.                                                          |
| `isDefault`   | Whether new work of this kind starts here. Exactly one per set.                                                             |

**`key` is immutable because it is stored in more places than the status row.** Every piece of work
carrying the status stores it, and so do saved-view predicates, automation-rule parameters, and
connector mappings. A rename that rewrote the key would silently empty a saved view and stop an
automation from firing. So a rename moves `name` and every one of those keeps resolving. The key
never reaches a person: it is generated once from the name and never shown as something to edit,
and `WorkStatusUpdate` has no `key` field at all.

**Board order is category rank, then position.** The five categories have a fixed display rank
(`WORK_STATUS_CATEGORY_RANK`, running `backlog → unstarted → started → completed → canceled`), and
`compareWorkStatusOrder` is the one exported comparator that the API resolver, the settings list,
and every picker sort by. Reordering therefore happens **within** a category: a workspace decides
whether `Awaiting signature` comes before or after `Under review` among its `started` statuses, and
the fact that started work reads above finished work is Docket's. A list then reads top to bottom
as work progresses, in every workspace, without anyone having to arrange that.

**A status has no colour.** The category owns the colour, through the `--state-*` tokens
`DECISIONS.md` pins to the taxonomy. This is what lets someone glance at another team's board and
recognize what they are seeing without learning that team's palette, and it is why the taxonomy
being fixed buys more than it costs. See _Not built_.

### Where a set lives, and forking

Statuses are **workspace-owned**. A `work_status` row with a null `team_id` belongs to the
workspace set for its `entity_type`, and every team follows it.

**A team may fork the Task set.** Forking copies the workspace's Task statuses into rows owned by
that team; the team then edits them freely, and changes to the workspace set stop reaching it.
Resetting gives those rows up, and the team follows the workspace again. A team that holds any Task
status rows of its own resolves to them; a team that holds none resolves to the workspace's.
`WorkStatusSetOut{ entityType, teamId, forked, statuses }` reports which of those happened, so a
caller reads one shape either way.

**Only Tasks fork**, because only Tasks are team-scoped. Projects, Programs, and Initiatives belong
to the workspace, so a team-scoped set for them would have no one to apply to; a CHECK constraint
(`work_status_team_scope`) makes such a row unstorable rather than merely discouraged.

### How work points at its status

Each of `task`, `project`, `program`, and `initiative` keeps the key column it has always had
(`task.state`, `project.status`, `program.status`, `initiative.status`) and gains `status_id`
beside it. The two are bound by a **composite foreign key** over
`(status_id, <key column>, organization_id)` referencing `work_status (id, key, organization_id)`.

Referencing the triple rather than the id alone is the point of the shape. It makes the pair
provably consistent — a row whose key disagrees with the status it names does not store — and it
makes a cross-tenant status unrepresentable for the same reason. The wire contract is unchanged:
the forty-odd readers, connectors, saved views, and API responses that have always used the string
keep working untouched, and the database now guarantees what they were trusting. `ON UPDATE
CASCADE` turns a key rewrite into one statement instead of a cross-table backfill. `ON DELETE
RESTRICT` is what requires a status deletion to remap its work first.

### Programs can complete

The seeded Program set is `Proposed · Active · Paused · Completed · Archived`. `Completed` records a
Program that reached its end, and `Archived` (category `canceled`) records one retired and kept for
history; `Proposed` mirrors Initiatives. A Program is still generally an ongoing concern and is
still read through health and flow rather than a progress bar — that distinction from a bounded
Project is real and is stated in the product. Withholding a `completed` value from every workspace
made the distinction look enforced while forcing an opinion on the nonprofit whose after-school
program genuinely ended last June. A workspace that wants Programs which only ever end by being
archived deletes `Completed` from its Program set.

### What a new workspace starts with

`DEFAULT_WORK_STATUSES` is the single seed source, read by workspace creation, by the migration
that backfilled existing workspaces, and by the tests asserting both.

| Kind       | Seeded set (default in bold)                          |
| ---------- | ----------------------------------------------------- |
| Task       | **Backlog** · Todo · In Progress · Done · Canceled    |
| Project    | **Planned** · Active · Completed · Canceled           |
| Program    | Proposed · **Active** · Paused · Completed · Archived |
| Initiative | Proposed · **Active** · Completed · Canceled          |

Every workspace renames, reorders, adds to, and deletes from these afterwards. `0087_sour_post.sql`
seeded existing workspaces from the shape most of their teams already shared and forked only the
teams that differed, so no customization was lost.

## API surface

`/v1/orgs/:orgId/statuses`. One surface for all four kinds, discriminated by `entityType`. Reading
requires `org:view`; every mutation requires `org:manage`. The DTOs in
`packages/types/src/work-status.ts` are authoritative, and `api-rpc-contract.md` §3.2 carries the
route table.

| Route                        | Body                                              | Returns                                            |
| ---------------------------- | ------------------------------------------------- | -------------------------------------------------- |
| `GET /statuses`              | `query: { entityType?, teamId? }`                 | `WorkStatusSetOut[]`, each in board order          |
| `POST /statuses`             | `WorkStatusCreate`                                | `WorkStatusOut`                                    |
| `PATCH /statuses/:statusId`  | `WorkStatusUpdate`                                | `WorkStatusOut`                                    |
| `POST /statuses/reorder`     | `WorkStatusReorder{ entityType, teamId?, order }` | `WorkStatusSetOut`                                 |
| `DELETE /statuses/:statusId` | names the replacement the work moves to           | `WorkStatusDeleteResult{ deleted, remappedCount }` |

Three behaviours worth stating in prose:

- **`WorkStatusCreate.position` is optional**, and omitting it appends the status after the others
  sharing its category. `teamId` on create adds to a team's own Task set and is accepted for Tasks
  only.
- **`WorkStatusUpdate.category` moves work with it.** Work already sitting in the status has its
  completion recorded or cleared to match the new category, because a status changing from
  `started` to `completed` is a claim about the work, not only about the label.
- **`WorkStatusUpdate.isDefault` accepts `true` alone.** Making a status the default is a move, so
  there is nothing a `false` would mean beyond "leave the set with no default", which the set is
  never allowed to be.

## Invariants

Each of these is enforced in the database, so no writer can route around it.

| Invariant                                        | Enforced by                                                   |
| ------------------------------------------------ | ------------------------------------------------------------- |
| A key is unique within one set                   | `work_status_ws_key_uq` / `work_status_team_key_uq` (partial) |
| At most one default per set                      | `work_status_ws_default_uq` / `work_status_team_default_uq`   |
| A work row's stored key equals its status's key  | the composite FK on each of the four tables                   |
| A status and the work carrying it share a tenant | the same composite FK, via `organization_id`                  |
| A status in use cannot be deleted                | `ON DELETE RESTRICT`                                          |
| Only a Task status may belong to a team          | `work_status_team_scope` CHECK                                |
| `position` is non-negative                       | `work_status_position_nonneg` CHECK                           |
| A key and a name are non-blank                   | `work_status_key_not_blank`, `work_status_name_not_blank`     |
| A status is never archived                       | `work_status_never_archived` CHECK                            |

The workspace set and a forked team's set are different sets, which is why the key and default
uniques come in pairs of partial indexes: both may hold a `done`, and each needs its own answer to
"where does new work land".

**A status is deleted with an explicit remap and never soft-deleted.** `archived_at` is constrained
to stay null. An archived status would keep the work sitting on it while vanishing from every
picker, leaving people looking at a status they cannot select and cannot leave — worse than either
alternative, so the schema refuses it and deletion asks for the replacement instead.

Two behaviours live in the application because they read across rows: entering a status whose
category is terminal (`completed` or `canceled`, per `TERMINAL_CATEGORIES`) stamps the owning row's
`completedAt` or `canceledAt`, and leaving one clears both; and creating work with no status named
resolves the set the owner falls under and takes its `isDefault` row.

## Not built

- **Per-status colour.** The category owns the colour, so one glyph means one thing across every
  board in a workspace and a person reading another team's list recognizes it on sight. A picker
  would hand each set five to fifteen independent colour decisions and return nothing the category
  was not already saying. This is the reinforced form of the `DECISIONS.md` entry keying colour
  tokens to the taxonomy.
- **Custom categories.** The five are fixed and are not user-definable. Every consumer — status
  glyphs, cross-team grouping, progress and capacity maths, and every integration mapping — reads
  the category rather than the key, and holding it still is precisely what keeps all of them
  correct for statuses nobody has invented yet. A sixth category would be a value each of those
  consumers has no rule for.
- **Cycle statuses.** A Cycle's status follows its window: it is upcoming, active, or completed
  according to its dates. Letting someone set it by hand would let a Cycle claim to be active in a
  week that has passed. `cycle_status` therefore stays a fixed enum and `WorkStatusEntityType`
  omits `cycle`.
- **Per-team sets for Projects, Programs, and Initiatives.** Those three are workspace-scoped, so a
  team-scoped set for them would have nothing to apply to.
- **Transition rules.** Any status in a set can be moved to from any other. Constraining which
  moves are legal is a workflow engine, and the product's answer to "this should only happen after
  review" is an automation rule (`automations.md`).
