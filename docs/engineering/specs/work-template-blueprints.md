# Work-template blueprints

Delivery layer 2 of the [approved work-template overview](../../superpowers/specs/2026-09-14-work-templates-overview-design.md).
This extends the [identity and version contract](work-template-identity.md) with composed work,
relative timing, selective updates, and retained scheduler compatibility.

## Scope and governing rules

A published work-template version defines an optional blueprint. Creation produces the root and every selected descendant in one transaction, with a maximum of **500 new rows including the root and Milestones**. A root with 499 descendants is valid; one with 500 descendants is refused. Manual creation, MCP, accepted plans, captures, imports, connectors, and recurrence use one creation service. Database base-identity guards remain defense in depth; a SQL trigger does not expand a blueprint.

The layer delivers nested templates, optional children, relative dates, parent-relative assignment and cycle rules, generated-child provenance, selective update/change previews, archive impact, and Save as template. It replaces the work-insertion part of process blueprint execution while preserving schedule cadence, horizons, exceptions, calendar bindings, occurrence identity, and public compatibility adapters. Existing process/scheduler tables and mapping projections remain until layer 3 verifies their retirement. Program schedule management and default schedules (D23–D26, D44), gallery installation/cross-workspace transitive copy, Athena proposals and commercial gating remain later layers. Existing recurrence integration is required now; a new Program Schedules product surface is not.

Published definitions stay immutable. No update removes authored prose, title, manual dates, hand-added children, or completed/canceled work. A root's current template version is distinct from each descendant's creation provenance and individually accepted timing bindings. A template has no literal person, team, Project, Program, Milestone, Cycle, or absolute-date reference in its reusable payload. The existing explicitly documented `labelIds` exception remains: labels are tenant-validated, destination-scope-resolved, and missing labels are dropped with preview warnings. Template ownership and administrative team offerings remain metadata, not blueprint assignments.

## Concrete contracts

Add leaf contracts to `domains/work/src/contracts/work-template-blueprint.ts`, separate from existing work-row contracts to avoid the Task→Template import cycle. Add branded `BlueprintStepId` to `domains/work/src/ids.ts`. Reuse `WorkTypeId`, `WorkTypeVersionId`, ordinary per-kind starting-field enums, and strict ISO civil-date validation.

`Blueprint` is `{ steps: BlueprintStep[], dependencies: BlueprintDependency[] }`, defaulting to empty when omitted. A version accepts at most 499 authored steps and 2,000 dependency edges; the fully expanded graph also caps combined edges at 2,000, and its worst-case transitive expansion remains at most 500 rows. Keys match `[a-z][a-z0-9_-]{0,63}` and are unique within that version. Preserve a key across edits to the same logical step; changing a key deliberately means removal plus addition. Sort is a nonnegative integer; ties use key order. Bounds are validation limits, not exceptions to the 500-row expansion check.

Each strict `BlueprintStep` has:

- `key`, `kind: 'program' | 'project' | 'milestone' | 'task'`, `parentStepKey: StepKey | null`, `sort`, and `optional: { enabled: boolean; selectedByDefault: boolean }`. `selectedByDefault` must be true when `enabled` is false.
- `template: null | { workTypeId; selection: { kind: 'latest' } | { kind: 'pinned'; workTypeVersionId } }`. A referenced template must have exactly the step's kind and tenant. Milestones require `template: null`.
- `fields`, discriminated by kind: required nonblank `name`/`title`, optional summary, Markdown description, ordinary priority/health/status-key fields where supported, task `labelIds`, task `estimate` and `estimateMinutes` (nonnegative ordinary task units), and Program visibility. Exclude all literal placement/actor/team/date IDs. Starting-draft payload fields and step overrides use the same validators; arbitrary JSON properties are rejected.
- `teamRule: 'parent_team' | 'creation_team' | 'none'`, `actorRule: 'parent_responsible' | 'creator' | 'athena' | 'unassigned'`, and task-only `cycleRule: 'none' | 'parent_cycle' | 'current_cycle'`. Fields unsupported by the kind are absent, not ignored.
- `dates`, a strict map of supported fields: Initiative has no child-step kind; Program has no dated fields; Project has `startDate` and `targetDate`; Milestone has `targetDate`; Task has `startDate` and `dueDate`. Each value is a `BlueprintDateRule` below. An omitted field means undated and unmanaged.

A plain inline step (`template: null`) gets the kind's currently resolved base identity, but does not recursively expand the base blueprint. Its own authored child steps define its structure. Explicitly referencing a base template expands that base like any other named template. Normal root creation from a base still expands its blueprint. This distinction prevents implicit self-recursion and duplication when Save as template captures inline children. Inline starting values may fill absent fields from the resolved base; explicit blank description is preserved.

A template-backed step merges referenced starting values, step overrides, and explicit creation/schedule overrides in that order. Single-line step titles fill blanks rather than erase authored titles. Markdown follows the existing append policy. For root clients that already applied the template locally, present description is the final authored value and must not have the outline appended a second time. Root API explicit values keep layer-1 precedence; clients use the shared merge helper when selecting a template. Blueprint child override documents append to the referenced outline once; creation context identifies a prepared final document internally so no second pass appends it again. Extract the browser-independent helper from `apps/web/src/components/templates/merge.ts` to `domains/work/src/template-merge.ts`, retaining a web re-export.

`BlueprintDependency` is `{ blockerStepKey; blockedStepKey }`, distinct, unique and task-to-task within one authored blueprint scope. Edges identify the authored step's root Task, not every nested subtask. No cross-template-private step keys, external task IDs, or dependencies on Milestones/containers. The pure planner maps valid edges to ordinary task-dependency rows after all new IDs exist.

`WorkTemplateDefinition` gains `blueprint: Blueprint` with a read-time empty default. New draft saves/publishes serialize the field. Historical published JSON lacking it remains byte-for-byte unchanged; parsing supplies the empty value without rewriting the version. Canonical equality checks normalize both sides at read time, including `legacyTemplateDefinition` pending-draft detection, so the new empty default does not falsely flag every older publication as a dirty draft. Legacy starting-draft edits preserve the existing blueprint unless using an explicit canonical draft edit. Empty legacy PUT-like payloads cannot silently erase children.

### Shared service and planner shapes

`WorkKind` aliases the existing `TemplateTargetType`; `StepKey` is the validated logical key above. The following names are concrete extraction contracts. Zod mirrors public shapes; internal types carry already validated branded IDs and snapshots. `WorkCreateBodyByKind` maps to the existing four create bodies rather than inventing another vocabulary.

```ts
type OptionalChoice = { path: readonly StepKey[]; selected: boolean };
type BlueprintSelection = { workTypeId: WorkTypeId; workTypeVersionId?: WorkTypeVersionId };
type ResolvedBlueprintGraph = {
  root: PublishedBlueprintSnapshot;
  publications: readonly PublishedBlueprintSnapshot[];
  resolutions: readonly {
    path: readonly StepKey[];
    workTypeId: WorkTypeId;
    versionId: WorkTypeVersionId;
  }[];
  fingerprint: string;
};
type ResolvedBlueprintInput = {
  graph: ResolvedBlueprintGraph;
  root: ResolvedRootDraft;
  context: BlueprintCreationContext;
  choices: readonly OptionalChoice[];
};
type WorkCreationCommand<K extends WorkKind = WorkKind> = {
  caller: ActorCtx;
  kind: K;
  body: WorkCreateBodyByKind[K];
  blueprint?: {
    previewToken?: string;
    creationTeamId?: TeamId;
    optionalChoices: readonly OptionalChoice[];
  };
  invocation: TrustedCreationInvocation;
};
type WorkCreationBatchCommand = {
  roots: readonly { key: string; command: WorkCreationCommand }[];
  edges: readonly ResolvedInvocationEdge[];
  invocation: TrustedCreationInvocation;
};
type WorkCreationResult = {
  root: InsertedWork;
  created: readonly InsertedWork[];
  changeSetId: string | null;
  resolvedManifest: readonly ResolvedVersionAtPath[];
  effects: readonly DeferredWorkEffect[];
};
type WorkCreationBatchResult = {
  rootsByKey: ReadonlyMap<string, InsertedWork>;
  created: readonly InsertedWork[];
  changeSetId: string | null;
  effects: readonly DeferredWorkEffect[];
};
```

`PublishedBlueprintSnapshot` contains tenant, kind, template/version IDs, immutable definition and projected step IDs. `ResolvedRootDraft` is the kind-correlated body after default/status/label/placement resolution. `BlueprintCreationContext` holds authorized references, responsible-actor/team/cycle snapshots, civil creation/run date, timezone, weekdays, completion facts and schedule overrides. `TrustedCreationInvocation` holds a provenance context, existing replay key and allowed archive-binding capability; construct it in existing entry adapters, never parse it from untrusted JSON. `InsertedWork` is `{kind,id,row}` where row remains kind-correlated; `ResolvedVersionAtPath` records exact publication at a qualified path. `DeferredWorkEffect` is a typed existing event/index/assignment effect whose dedupe key belongs to the committed action, not an arbitrary callback supplied by clients.

`ResolvedInvocationEdge` names validated root+step paths within the trusted legacy/plan forest and an ordinary dependency edge; public templates still restrict dependencies to their own authored sibling scope. `WorkCreationBatchCommand.roots` are nonempty and unique by key. The aggregate limit counts every new row, including explicit create-body Milestones/children as well as blueprint descendants; combined dependencies are capped at 2,000. All trusted batch roots share one tenant/provenance authority; cross-workspace batches are rejected. Client optional-choice lists are unique, known paths, maximum 499. Unknown, duplicate or nonoptional paths are 422; absent entries use authored defaults. `BlueprintDiffInput` contains mode, authorized current tree/bindings, selected resolved graph, context and choices; `BlueprintDifference` is exactly the child-change union in the preview section. `PlannedWorkTree` has root/parent-ordered nodes, qualified paths, resolved rules/dates, dependency path pairs and warnings; no concrete new IDs or side effects. `BlueprintReflowInput` is the existing date graph, proposed anchor/completion facts, bindings, weekday snapshot and terminal-state facts; `PlannedDateChange` identifies one existing row/date field and its new value/binding. `CapturableWorkTree` contains only authorized concrete rows/relations; `CapturedTemplateDraft` contains definition plus review warnings and no source work IDs in its reusable payload.

## Hierarchy and scope

Use the existing physical model, not new work kinds:

| Blueprint owner | Immediate children | Placement                                                                                   |
| --------------- | ------------------ | ------------------------------------------------------------------------------------------- |
| Initiative      | Program, Project   | Create ordinary rows and Initiative associations; no containment edge is invented.          |
| Program         | Project, Task      | Project.programId / Task.programId.                                                         |
| Project         | Milestone, Task    | Milestone.projectId / Task.projectId.                                                       |
| Milestone step  | Task               | Task.projectId remains the containing Project; Task.milestoneId is the generated Milestone. |
| Task            | Task               | Task.parentTaskId, inheriting valid Project/Program/Milestone context.                      |

No Initiative child step, nested Program under Program, Project under Project, or Milestone outside a Project. A Task template may reference another Task template; cycles are still forbidden. A generated Project/Program in an Initiative expansion is linked to that Initiative, including Projects reached through its generated Programs. These links are explicitly part of this creation, not a rule that linking any existing Program automatically links all its Projects.

A `parentStepKey` resolves only in its authored version. Local descendants attached to a template-backed step are additive to that template's expanded children and obey the same placement matrix. Keys are qualified in the flattened plan by the complete expansion path, so two Vendor booking instances with `get_quote` produce distinct children and dependency targets. Client paths are arrays of keys, never slash-concatenated ambiguous strings.

Validate containment as a forest rooted at the work item. Validate template expansion with a DFS stack of **template identities**, not just version IDs: A(v1)→B(v2)→A(v3) is a loop and names the full accessible loop in the refusal. Also validate a combined date-prerequisite/dependency DAG; a dependency cycle or a completion-relative cycle is refused even when containment is acyclic. An optional Milestone/parent owns its whole subtree. A selected consumer cannot reference an unselected optional parent, blocker, or timing anchor: preview identifies the prerequisite; acceptance returns 422 unless the selection is closed. UI keeps prerequisite selection explicit rather than silently creating unchecked work.

## Nested version resolution and publication

`resolveBlueprintClosure(tx, selection, mode)` reads only authorized publications and returns `ResolvedBlueprintGraph`: root snapshot, map of path→exact template/version, normalized steps, offerings, and a content fingerprint. Resolve every occurrence of one `latest` template to the same version within a request. A pinned occurrence may intentionally use another published version. Resolve under one SERIALIZABLE transaction/snapshot; acquire definition locks in sorted ID order before publication/mutation. Where closure discovery requires more rows, restart resolution with the complete lock set; bound retries through existing `serializableTx` (three attempts). Never make provider calls or take pooled-client reads while that transaction holds its connection.

Publication checks the complete worst-case graph with all optional steps selected. Creation checks again with current latest child versions and actual choices. Thus a valid parent publication may later fail creation if a latest child grew beyond 500 or now closes a loop; return a named actionable conflict, never partial work. Pinned references always retain their exact publication. The Settings projection reports newer pinned children. Republish creates a new parent version containing the reviewed newer pins: publication preview shows each refresh, and acceptance supplies those exact version IDs plus the draft revision/fingerprint. Old parent versions never acquire new pins. Latest references remain latest references; the creation receipt stores their concrete resolutions.

New publications may reference only active, published, workspace-visible templates, never private/team drafts. Publication checks offerings for structural validity but only creation knows actual destination teams. Archive does not destroy versions. Parents already published with a now-archived child may continue expanding that retained reference; authors cannot add a new archived reference. Ordinary creation cannot directly choose an archived root. Existing schedules bound before archive continue using their authorized root/publication. This is a service capability derived from the existing series binding, not a public `allowArchived` request flag. Newly restricted offerings do not strand an existing schedule's binding, but current work/resource permissions still apply.

## Parent, team, actor, and cycle resolution

An internal `BlueprintCreationContext` carries authorized tenant, initiating actor, provenance, destination (ordinary existing resource references), a fallback creation team, creation date, civil-date timezone, optional scheduler run date and schedule-specific overrides. Row references belong here or in a schedule draft, never in the reusable definition. Resolving rules is pure against an authorized snapshot; checking those snapshot rows is an API responsibility.

- Responsible actor means Task.assigneeId, Project.leadId, Program.ownerId, or Initiative.ownerId. Milestones delegate team/responsible/cycle context to their containing Project. Missing parent responsible actor means unassigned. `creator` means the recorded initiating actor; scheduler runs use the series' authority actor, not a fabricated cron human. `athena` resolves the tenant's active Athena actor through existing actor infrastructure. Missing/inactive relative actor or Athena produces unassigned plus a bounded warning; no session is created. Recheck assignability and scope at acceptance.
- Parent team means Task.teamId, Project.teamId, Initiative.leadTeamId, or inherited creation team for Program. Program has no team column. `creation_team` is the explicit authorized destination fallback. `none` is allowed only for kinds whose ordinary schema permits no team. When the parent has no team value, an explicitly supplied authorized creation team is the fallback for parent_team as well. Task.teamId is required; unresolved task team fails the whole preview/create with a field-level requirement to choose a creation team. Never choose the first tenant team or leak literal teams into a template.
- Task parent cycle comes from the nearest Task ancestor with a cycle. Project/Program do not have implicit cycle columns. `current_cycle` uses the resolved task team and the root creation/run civil date within that team's current nonarchived cycle window. Zero matches produces no cycle with a warning; multiple matches is an integrity error. A closed/foreign/different-team parent cycle does not attach: produce no cycle with a warning, or reject an explicit creation override. Cycle lookup is frozen for this creation and does not move later because time advances.
- Relative assignment does not authorize creation in a destination the caller cannot use. Existing `resolveResourceAccessForActors`, `requireWorkAccess`, shared-work capability checks, reference validators and destination membership rules remain authoritative. New children inherit a visibility/access scope no broader than their root and placement allow. The service must not widen a private Program's generated work by using public defaults.

### Creation authority and existing permission thresholds

Preserve the ordinary Program creation requirement of `manage`, including a Program generated
inside an Initiative blueprint. Other generated kinds retain their existing live creation and
destination checks. A contributor cannot gain structural creation rights through MCP or a nested
template; refuse the entire tree before writes when a required right is absent.

Foreground commands carry the real `ActorCtx`. Existing authorized integration, routing, and
scheduler adapters may carry a trusted internal creation authority instead, preserving their
current nullable creator and scoped provider/rule authority. Do not fabricate an actor or turn
`createdBy: null` into an authorization bypass. Model the internal command's caller as the
kind-correlated union of actual actor context and trusted adapter authority; the latter is never
parsed from REST/MCP JSON. Recheck the adapter's existing tenant/resource authorization in the
same transaction. This is the existing authority path made explicit, not a second permission
system or a new public system-creation capability.

## Date-only timing

`BlueprintDateRule` is a strict discriminated union:

- `{ kind: 'none' }`.
- `{ kind: 'anchor'; anchor: { kind: 'parent' } | { kind: 'milestone'; stepKey }; offset: DayOffset; snap?: WeekdaySnap }`.
- `{ kind: 'after_completion'; stepKeys: StepKey[]; offset: DayOffset; snap?: WeekdaySnap }` with one or more distinct sibling Task keys and a nonnegative offset.

`DayOffset = { days: integer[-36500,36500]; unit: 'calendar' | 'working' }`; completion-relative days use `[0,36500]`. `WeekdaySnap = { direction: 'next' | 'previous'; weekday: ISO1..7; inclusive: boolean }`, default `inclusive:false` (“following Monday” means strictly following). Apply signed day offset first, then snap. Zero working days leaves the anchor unchanged even on a weekend. Positive/negative working counts exclude the anchor day and count only configured working weekdays. Snapping is a calendar-weekday operation regardless of working-weekday membership. Overflow outside ordinary work-date range is a validation error.

Add workspace `workingWeekdays: ISOWeekday[]` to Settings→General, admin-editable, nonempty, unique, sorted, default Monday–Friday `[1,2,3,4,5]`. This belongs to the workspace; do not substitute a particular person's work schedule. Extract the existing pure civil arithmetic from `domains/planning/src/calendar-date.ts` into `domains/work/src/calendar-date.ts` and retain the planning module as a compatible re-export. Planning already depends on work; work must not depend back on planning. Preserve the existing arithmetic behavior and exports, with no duplicate date engine, server-local timezone calculations, or holidays in this layer. Use existing schedule timezone for runs; otherwise freeze the creator's resolved planning timezone (existing UTC fallback) in root generation metadata. Completion instants are converted to civil dates in that stored timezone. Storage adapters preserve ordinary existing date representation and planning-date resolution metadata; generated dates use day resolution. A coarse Project/Initiative target resolves through the existing planning-date boundary policy, not an invented mid-period day.

Anchor sources: Initiative.targetDate, Project.targetDate, Task.dueDate, or Program's creation civil date. A scheduled Task/Project uses the run date as its due/target anchor. Milestone-relative Task dates use the generated Milestone.targetDate, which can itself derive from the containing Project. A nested template's children count from that generated item's own anchor; propagation follows the topological date graph.

Missing anchors create all selected work immediately with managed dates null and `unresolvedReason:'missing_anchor'`; no work creation is delayed. Filling/moving an anchor recalculates managed descendant dates in the **same transaction**. Reflow is capped at 500 affected descendants as well as each creation's cap. If manual additions have made a larger affected tree, refuse that anchor write with an actionable preview requirement; never partially redate or silently truncate.

After-completion timing waits until all listed sibling Tasks are completed, then anchors to the latest actual completion civil date. Canceled is not completed; missing/skipped prerequisites cannot satisfy it. Reopening a predecessor clears/recomputes only unpinned, nonterminal dependent dates in the same state transition; cancellation leaves them unresolved. A manually set dependent date stays. Completing a sibling does not create new rows. Repeated delivery of the same transition is a no-op. Existing task completion, timer, parent/subtask and automation semantics still execute once through `task-state.ts`.

Working-weekday changes affect future resolution/reflow but do not launch an organization-wide rewrite. Root receipts record the calendar snapshot used. Anchor/explicit preview operations read current weekdays and bind them into the reviewed token; retries retain the same resolved context, and a concurrent calendar change invalidates acceptance. Completed/canceled work and terminal descendants retain their historical dates.

## Persisted provenance and partial adoption

Use the existing work rows plus immutable step projections, not replacement process-instance/mapping tables. Retain the old process-instance/mapping tables only as legacy compatibility projections until layer 3; canonical work never depends on them:

1. Add immutable `blueprint_step` projections keyed by `(id, version_id, organization_id)`, with unique `(version_id,key)`, kind, local parent key, sort, and validated typed rule/field data. `work_type_version.definition.blueprint` is the canonical publication; the rows are its FK/index projection, inserted by `templates/persistence.ts` in the same publication transaction. Freeze both, validate projection equality at the persistence boundary, and prevent independent step edits. `blueprint_dependency` is the immutable edge projection with same-version/tenant endpoint FKs. Historical versions without blueprint have zero rows.
2. All four work tables plus Milestone receive nullable `blueprint_step_id`, `blueprint_source_version_id`, `blueprint_parent_kind/id`, and `blueprint_path` (qualified keys). A trusted legacy forest root may have no work parent; its retained occurrence/invocation receipt identifies the origin instead of an invented parent. Composite FKs bind step/source/tenant. Tenant/kind-aware guards verify the actual parent exists and the step kind matches the child. This is origin data: changing the work's template never rewrites who created it. Hand-added work has no step.
3. Add typed `blueprint_date_bindings` per supported date field: `{ sourceStepId, sourceVersionId, rule, manual, lastDerivedDate }`. `manual` is server-maintained and defaults false for generated bindings. Store the current accepted rule for each field independently. This permits adopting a new due-date offset while retaining the old start-date rule. Creation provenance remains immutable; accepted rule provenance changes only for the explicitly chosen field.
4. Add root `blueprint_state` containing monotonic revision, generation key, resolved path/version manifest, optional selections, creation timezone, last calendar snapshot, and last application change-set ID. Bound it to the 500-node graph and do not serialize the full object on ordinary rows/search. Per-generated-row `blueprint_ever_started` is monotonic: started/completed transitions or recorded actual work set it; moving status back to unstarted cannot make removal cancellation safe again.

An ordinary authorized explicit date patch, even setting the same date or null, sets that field's manual marker in the same write. Imports/provider edits are explicit ownership as well. An anchor-derived write changes only derived fields and never pretends to be manual. An explicit **Follow template date** action previews the current derived date and clears the marker on acceptance; changing the parent anchor never clears it. Preserve range resolution and user-edited prose. Deleting/detaching a generated child remains an ordinary explicit work operation; do not recreate it on unrelated anchor writes. A later update preview can offer missing work explicitly.

## One creation path and transaction contract

Add `apps/api/src/lib/work-creation/{service,writers,context,effects}.ts` as focused extractions of existing behavior, not another repository/DAO. Existing Drizzle tables, authorization, status, label, placement and provenance helpers remain the only writes. API service signatures:

- `createWork(command: WorkCreationCommand): Promise<WorkCreationResult>` owns `serializableTx` when the caller has none.
- `createWorkInTransaction(tx: TemplateTransaction, command: WorkCreationCommand): Promise<WorkCreationResult>` joins an existing plan/occurrence/undo transaction; never starts a nested transaction.
- `createWorkBatchInTransaction(tx: TemplateTransaction, command: WorkCreationBatchCommand): Promise<WorkCreationBatchResult>` is the trusted existing-plan/legacy-forest adapter. It plans all roots with one frozen context, validates the combined dependency/date graph and aggregate 500 cap, and uses the same non-expanding dispatcher/receipt/effect drain; it does not independently call a single-root public endpoint per root. It has no new public REST/MCP endpoint.
- `insertWorkRow(tx, input: ResolvedWorkInsert): Promise<InsertedWork>` is the shared **non-expanding** per-kind insert dispatcher extracted from current routes/placement. Milestones use `insertMilestones`. `matchExisting` remains a separate placement decision before this dispatcher; blueprint nodes always insert fresh rows and never coalesce equal names.
- `resolveBlueprintClosure`, `loadBlueprintCreationContext`, and `applyBlueprintPlan(tx, context, plan)` use the caller's transaction. Pure `planBlueprint(input: ResolvedBlueprintInput): PlannedWorkTree` reads no database, generates no ULIDs, calls no clock and emits no events.

Flow: validate root/destination live access → resolve exact closure/context → plan and validate selected count/date/dependency graph → allocate ULIDs with existing genId → insert root and descendants in parent order → create labels/associations/dependencies and rule bindings → record one existing provenance change set/idempotency receipt → commit → drain deferred effects. All failure paths roll back root, Milestones, children, dates, links, images and receipt. An after-commit effect failure never makes the client retry creation as if it did not commit.

Every new-row writer in `apps/api/src` must delegate: ordinary four routes; MCP organize/capture/content; plan commit; recurrence; email acceptance; automation routing; calendar task links; time task anchors; voice/elicitation/agent dispatch; and integration reconcile/import/Notion branches. Existing-row sync updates do not expand again. Internal callers with no explicit selection still resolve the base through the service, so base blueprints work consistently. A database guard continues assigning complete identities to unsupported/raw inserts but cannot substitute for the application path.

Use existing idempotency keys for REST, change-set/action identity for MCP/plan, and occurrence uniqueness for scheduler. Persist the final resolved manifest with the response/receipt: a retry after a child publishes must return the original tree, not a second expansion. Allocation/resolution occurs within the replay-safe transaction; existing serializable retries may regenerate rolled-back IDs but emit no side effects until commit. One user action has one undoable change set and **one assignment notification per assignee**, with all assigned created items included. Ordinary task assignment triggers still receive their tasks; aggregate notification delivery must not merge away automation work. Extend existing tracked-kind support for Milestones if needed; do not introduce a second undo engine.

## Creation, update and change previews

Extend the existing assignment route/service and typed query definitions. Keep old identity-only calls valid and default starting-field application off.

- Creation uses a new typed `POST /templates/definitions/:id/blueprint-preview` with kind-correlated root draft, selection, destination and optional choices. Response: exact root/version manifest fingerprint, at most 499 descendant summaries (`path`, kind, title, template/version, dates, unresolved reasons, optional/default/selected flags, prerequisites), counts/warnings and `previewToken`. Summary titles are display-truncated to 256 characters; full bodies are omitted. Warnings are distinct typed codes with affected-path counts, maximum 100 records, and overflow is represented by an aggregate count. Responses include no raw private draft definitions. Existing create bodies gain optional `blueprint: { previewToken?, creationTeamId?: TeamId, optionalChoices: {path, selected}[] }` with optionalChoices defaulting to[] and resolved against authored defaults. `creationTeamId` is an ordinary live-authorized invocation reference, never saved into the template; it lets a teamless Program/Initiative context create required-team descendants. The preview destination carries the same value. Omission uses authored optional defaults and server resolution. Explicit nonempty optional choices require a valid preview token. A creation-team-only request may resolve server-side without a prior preview, preserving API/headless use while still checking rights. A create using a reviewed token conflicts if root draft, permissions, calendar, destination or latest resolutions changed. Offline drafts retain choices, tokens and authored work; reconnect requires fresh preview, never silent reset.
- Existing `POST /:id/template/preview` gains a `mode: 'change' | 'update'` defaulting to change, and a separate `childChanges` array bounded at 4,000 entries alongside existing maximum ten `changes` (at most 500 existing/new nodes, individual dates and the aggregate2,000 edges). `mode:update` requires the current template; `mode:change` requires a same-kind selected template. New `POST /:id/template/update` delegates to the same transaction-owning assignment service; current `POST /:id/template` remains change. Assignment adds `acceptChildChanges: ChangeId[]` defaulting to `[]`; omitting it retains identity-only or existing starting-field behavior and creates zero children. Explicit nonempty selections require the preview token. Stable typed Problem codes distinguish `blueprint_preview_stale`, `blueprint_limit`, `blueprint_loop`, `blueprint_prerequisite`, and `blueprint_destination_required` without exposing private names.
- Differences are keyed by opaque deterministic `changeId`, not array positions. Union: `add_child` (entire displayed subtree, count, selected optional defaults), `set_derived_date` (one child/date field, old/new/rule), `add_dependency`/`remove_dependency` for service-owned edges, and `cancel_removed_child`. A provenance match is source-template identity + qualified logical path, never title or concrete step ID across versions. Manual children are never matched/deleted by name. New child choices are initially selected, optional defaults respected; each addition can be unchecked. Date/dependency updates require explicit individual acceptance. Removed children are kept; cancellation is initially unchecked and offered only for backlog/unstarted work with no ever-started evidence. Milestones lack a cancel lifecycle and are only retained. Started, completed, canceled, shared/external-owned or inaccessible children cannot be silently canceled.
- Update mode never offers current root/child title or outline replacement (§5.4). Change mode retains layer-1 optional starting-field choices, all unchecked, plus new children; existing children and their origin bindings stay. Completed/canceled roots reject version-update mutation; open roots skip terminal descendants. Preserve the layer-1 explicit identity-only Change template contract on terminal roots, but offer/apply no starting fields or new children there. Root version becomes the reviewed publication even when some differences are declined; actual child bindings/selection state remain authoritative and another explicit preview can still identify unadopted differences.
- Token hashes canonical root/child revisions, membership/links, manual markers, active permission scope, resolved publications and offerings, calendar, selections and proposed differences. Acceptance locks root plus affected existing rows in deterministic order, rechecks all permissions, replans, checks token, applies selected operations and increments blueprint revision. Stale means 409, zero writes, retain choices as draft and show fresh review. Never trust client-supplied dates, body text or actor IDs hidden inside a child-change payload.

UI extends `work-template-change-preview.tsx` and the existing controller/query definitions; no component fetches or separate mutation pipeline. Creation summary reads “Creates 6 tasks and 2 milestones,” expands to dates and optional checkboxes, and clearly states missing anchor/prerequisite/team failures. Sample-item authoring uses relative timing controls and parent-based rules, with existing normal fields and shared primitives. Pinned-child updates appear in the Work templates workspace. No new work kind is added.

Authoring is a guided, re-enterable flow for defining the organization's work primitives. Purpose
establishes what the work is called, its existing kind, and when it is used. Work keeps the normal
sample document and compact child hierarchy central, revealing the selected child's fields, timing
and responsibility only when needed. Review presents the complete definition in human terms before
an explicit private save or workspace publication. A returning author opens Work directly and can
jump to any section. Switching sections preserves authored input, selection and editor position;
failed saves retain the draft, and leaving with unsaved changes offers a clear recovery choice.
One persistent save state and action area spans the full-page editor, with a clear return to Work
templates. Guidance must reduce the choices needed at each point without imposing a start-over
wizard on later edits. Configuration, publication history and engineering identifiers must not
obscure what the organization actually does.

The full-page flow uses MD3 Expressive containment and hierarchy. A prominent definition header
establishes name, kind and draft/publication state; contained navigation makes the three sections
recognizable. Distinct tonal regions separate the primary sample document, included-work outline
and selected-child editor. Secondary configuration, publication history and the persistent action
area have their own clear visual roles. Use the shared surface, shape, typography and motion tokens
to communicate grouping and importance at desktop and phone sizes, with intentional light/dark
themes. A flat page of equally weighted labels does not satisfy this interface contract.
These choices follow [Google's Material 3 Expressive principles](https://design.google/library/expressive-material-design-google-research),
which use containment, shape, type and color to direct attention and group related content.

## Archive and Save as template

Archive impact preview lists authorized active schedules using the definition and published parents referencing it, with bounded pagination/counts. No inaccessible work names or draft bodies leak. Archive refuses bases, removes new-create discovery, preserves immutable references and existing work/schedule execution. Unpublished unused drafts may follow existing deletion behavior. Any definition with work, child-reference or schedule use is retained/archived. Never cascade version/step deletion except authorized workspace purge.

Save as template is available on all four kinds under live work view rights plus authoring policy. `POST /:id/template/save-as/preview` first returns an authorized bounded capture and source snapshot token; `POST /:id/template/save-as` accepts new draft name and that source snapshot token; it creates a **personal unpublished draft** and opens the existing sample editor. It does not publish or mutate the source. Traverse only authorized work within the same placement/hierarchy rules; fail with a clear incomplete-capture result if hidden descendants prevent a faithful snapshot rather than leaking or silently labeling it complete. Capture no more than 499 descendants.

The capture is an independent inline snapshot of current outline/starting values and children, including edited generated work and manual additions. Do not reference the original nested template automatically; explicit template chips can be added during review. Current dates become calendar-day offsets from each actual parent's anchor; Milestone-associated tasks may use Milestone anchors. If a parent has no anchor, do not store literal dates: capture the child as undated with a review warning requiring timing choice. Specific actors map to parent_responsible, creator or Athena only when equal; otherwise unassigned with a warning. Teams map to parent_team/creation_team only when equal; otherwise require review, never retain IDs. Cycles map to parent_cycle/current_cycle only when equivalent; otherwise none with warning. Only dependencies between captured Task siblings survive automatically; external dependencies require review and are not turned into references. Preserve Markdown heading names and authorized document-image ownership through existing image-reference storage; no inaccessible attachment URL is copied.

Add nullable origin template/version metadata to the canonical definition for independent Save-as copies, consistent with D49; retain it when later layers copy or install definitions. This metadata is not a reusable work placement reference; no origin server learns of the copy. No cross-workspace lookup, gallery update UI or transitive install is introduced in this layer. Internal audit may name the source work; reusable public definition payload does not contain that work-row reference.

## Migration and legacy recurrence compatibility

Current physical tables are `template`, `work_type_version`, `work_type_team`, `process_definition/revision/step/*_spec`, `recurrence_series/revision/*`, `process_occurrence`, and `process_instance/*` mappings. Existing work identity is already enforced after journal 0152; process task identity additions are journal 0153. Do not mutate those migration SQL bytes or rerun their frozen backfill against evolving live contracts.

Use the next generated journal entries after the actual layer-1 tip (currently 0153): `0154_work_template_blueprints_expand` and `0155_work_template_blueprints_enforce` are intended names, not permission to overwrite an occupied number. Extend the existing checkpoint runner to apply **each boundary in order**: identity expand/backfill/enforce → blueprint expand/backfill/enforce → remaining standard SQL journal. The current final “apply all migrations” call must not leap over the new blueprint data checkpoint. Reuse `withMigrationPrefix` and the normal Drizzle journal/hash behavior; do not add a parallel migration history or migrator.

Expand adds nullable provenance/bindings, immutable step/dependency projections, weekday setting, occurrence root reference and canonical series selection/schedule-draft fields. Leave old execution tables readable. Historical version JSON remains unchanged; projection backfill uses the frozen migration format, not current defaults. A conversion checkpoint is tenant-scoped, batched, idempotent and keyed by retained source revision ID with unique mapping receipts, so interrupted conversion cannot publish duplicate templates. Scan incomplete rows repeatedly, not just IDs newer than the previous cursor.

Conversion rules:

- Single standalone task definitions become existing base-Task selection plus schedule-specific title/field/assignment overrides; no new menu template is created. A multi-step graph with one enclosing Project becomes that Project template plus its schedule selection. **A historical multi-root process remains a forest. Do not fabricate visible Program work or change any original destination to wrap it.** Convert its roots to kind-matched canonical selections and keep an immutable compatibility invocation manifest keyed by old process revision, with old root/step-key mappings, placements and cross-root edges. `createWorkBatchInTransaction` resolves/plans every root in one transaction and applies a shared500-row cap across the whole forest. The standard new product path remains one item with its blueprint; forest invocation is trusted plan/legacy glue, not a new template kind or public scheduling capability.
- Move literal teams/people/placements/cycles from old step specs into the series' **schedule draft/step overrides**, preserving actual assignments and destinations. Those immutable schedule revisions are location-specific and may contain validated row references. Never copy those IDs into published blueprint fields. An unscheduled legacy process with literals keeps them in a restricted compatibility invocation preset, not a menu template; invoking it passes that preset as creation context.
- Existing concrete instance mappings backfill each generated row's known step/source/path and occurrence root references. A legacy forest occurrence retains its original root list/key map rather than inventing a singular parent. Where a root has no canonical generating blueprint step, record its migration/recurrence origin and retained mapping receipt without manufacturing a step provenance claim. Do not recreate existing work. Existing nonnull dates are marked manual conservatively unless stored provenance proves they were derived and unchanged; preserving authored dates takes priority over guessing. Terminal rows remain byte-stable in body/status/dates/audit timestamps. Missing rows from historical `when_ready` instances are created only in a cutover transaction after access/reference/cap checks, then remain undated until prerequisites resolve. This is the approved all-at-once semantic replacement, not a claim that lazy physical row existence is preserved.
- Series/occurrence public IDs, cadence, revisions, weekdays, exceptions, skip/missed-run policy, rolling horizon, external-calendar occurrence keys and retry/dedupe behavior stay. Old REST/MCP define/schedule/repeat inputs are translated to canonical drafts and schedule context. Old process IDs/revision numbers/output key maps remain compatible through the migration receipts and legacy projections. Existing scheduler/definition adapters and process tables remain until layer 3 verifies retained data. Canonical creation results mirror the old instance mappings where legacy reads require them, in the same transaction; these are projections of the canonical work, not a second work executor. Compatibility authoring may maintain required old projections while its canonical selection is recorded. Historical creationMode is readable; new execution uniformly creates selected children at once. Document that semantic change in generated API descriptions.
- A retained graph over the cap or an untranslatable/foreign reference fails its checkpoint with an explicit source ID and safe remediation; do not truncate, silently drop steps, publish private bodies, or mark migration complete. Publishing/definition/scheduler writes are quiesced during conversion; normal work writers are rechecked until enforcement. Schedules cannot run halfway through conversion.

Enforce validates complete receipts, tenant/kind/parent references, date-binding shape, projections matching immutable JSON, archive guards, uniqueness and RLS under a restricted role. All future materialization routes call creation service. Independent old work-insertion execution stops; existing process/scheduler adapters, tables and necessary mapping/authoring projections remain operational until layer 3 verifies data and retires them. Do not make those projections read-only before their callers migrate. Physical removal is a separate verified layer 3 migration and is not bundled into cutover. A reverse deployment cannot run an old binary after canonical-only writes begin; recovery uses forward repair/backups and retained mappings, not deletion of new work.

### Compatibility forest ruling and cost

The legacy forest interface is a bounded engineering compatibility rule: preserve existing roots, work IDs, placement, assignments and occurrence outputs without adding visible grouping work. Its cost is one internal batch command, aggregate graph/count validation, immutable old-revision→root-selection receipts, and temporary mirroring of existing instance maps. It does not permit a second planner, work DAO or scheduler. Layer3 must prove that every legacy read/write caller and retained occurrence uses canonical data before retiring these projections.
