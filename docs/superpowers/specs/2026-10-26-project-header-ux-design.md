# Project header refinement

The approved project header puts icon, title and visibility/actions in one identity row,
with its editable outcome summary directly below. Owner, status, health and dates remain
visible on every pane width, wrapping naturally on phones. Program, initiatives and labels
are available through a labeled Properties popover. The main project action menu owns
current template identity/version, change/update/capture actions, repeat and trash.

Use the existing shared detail layout, property pickers and template preview/capture flows.
Add explicit presentation variants rather than change unrelated detail surfaces. Preserve
permissions, fiscal date precision, saved values, lazy option loading and keyboard focus.
The selected approach is a compact inline header. A permanent properties sidebar would
compete with the work body; retaining the existing adaptive overflow would hide essentials.

The broader typed-work exploration is UI/UX guidance only. This slice adds no new work type,
field, lifecycle, creation path or backend contract. Validate blank/populated projects,
long names, viewer permissions, metadata/template menus, narrow panes and both themes.

## Work type identity

The follow-up UI priority separates the work's type from its starting definition.
Default work reads Project (or the workspace's family noun), while a user-authored
name stays exactly as authored. The quiet type label sits outside the title heading;
no version appears beside it or in the project's main menu. Change work type opens
the existing guarded change review. Type definition details explicitly discloses
revision and template capture/update actions. This changes presentation, not saved
identity, definitions, data or permission semantics.
