# Plan and track work in Docket

Recommend the Docket Workflow: **define the outcome, choose the next work, do it, verify the result,
and update the plan.** Explain that enabled agents try to align substantive work with existing
Docket tasks/projects, honor explicit exceptions, and return authorized results to relevant records.
Explain the changes and try the approach the user adopts; do not reconfirm an existing request.

## Read the relevant guidance

- [The Docket Workflow](../../references/docket-workflow.md): explain practices, work structure, and cadence.
- [Agent assignments](../../references/agent-work.md): explain default alignment, task/project/initiative/program
  responsibilities, reporting rights, and exceptions. Read [Subagents](../../references/subagents.md)
  when the chosen workflow includes multiple workers.
- [Adoption](references/adoption.md): read the applicable section for first use, another tracker,
  repository conventions, interrupted setup, or blocked access.
- [Working in Docket](../../references/work-management.md): read before work tools for templates,
  workspace boundaries, authority, and saved-content checks.

## Guide adoption through real work

1. **Identify the problem.** Use existing context, workspace, and assignment. Ask only for information
   that changes the recommendation: where requests arrive, how work is chosen, or where results go.
2. **Recommend concrete changes.** State what the person and agent will do differently and why.
   Explain the assignment level and reporting behavior. Invite adoption or a specific constraint;
   do not present equivalent process menus or imply installation configured global enforcement.
3. **Try the chosen workflow.** Read the assigned record and relevant dependencies. Use
   [work-on](../work-on/SKILL.md) for execution/coordination, or the relevant capture, planning,
   updating, or review skill for that action. Load only what is needed. Perform authorized actions
   and verify results. A read-only introduction identifies useful next work without claiming execution.
4. **Make it repeatable.** Report the chosen changes, observed result, work reference if one exists,
   and where any requested convention was saved. Give a next prompt with its assignment level.
   Ask whether this addressed the problem and adjust the specific part that did not.

Distinguish proposed, saved, and verified results. Setup alone does not authorize imports, provider
connections, repository edits, scheduling, messages, timers, or Athena delegation. Explicit requests
need no second approval. If access fails, use [connect](../connect/SKILL.md), then resume this step.

Finish when the user has chosen the changes and tried them on real work. If access or a missing record
prevents that, report partial progress, propose the first task and its criterion, and identify the
next prerequisite. Do not invent links or sample work, put onboarding history in task descriptions,
or claim that discussing a convention configured automation.
