# Introduce Docket through the user's work

Read the section that matches the onboarding decision. Teach the workflow through the user's task,
not a product tour or a technical transcript.

## First use and returning users

Start with a real piece of work. Use existing conversation context; ask a focused question when the
outcome or current process is unknown. Explain Task and Project using that work: a task names an
actionable result, and a project groups tasks toward a finish line. Introduce Programs and Initiatives
when the distinction matters. Do not make the user configure an entire hierarchy first.

For an existing Docket user, read their records and terminology. For interrupted setup, resume the
known task and completed steps. Do not replay the welcome or create a replacement task. If the user
asked only to repair authentication, resolve access through `connect` and stop there.

## Explain what enabling Docket changes

Tell the user the default before demonstrating it: “For substantive work, I’ll try to find the
existing Docket task or project, read its requirements, and check the result against them. I’ll tell
you which work I’m using. You can ask me to work outside Docket for an assignment.” Explain whether
the adopted workflow includes state/result writes; do not imply installation alone authorized them.

Distinguish task execution from project coordination, initiative assessment, and program operation
using the user's work. Explain the level assigned and which decisions remain theirs. If subagents
are involved, explain their bounded deliverables, who records results, and the coordinator's combined
acceptance check. Use the shared agent and subagent references for the details.

Treat enabled alignment as the default rather than asking the user to approve each lookup. Offer
specific adjustments: automatic capture in an established destination, a different authoritative
tracker, task-only execution, or an explicit exception. Persist requested conventions in the chosen
guidance. Discussed preferences are not automatically installed global instructions or scheduled work.

## Recommend a specific change

Name the current problem and prescribe the relevant practice. For example:

“Your launch tasks are in Docket, but agents start from vague prompts and leave results in chat.
Start each agent session with its task link. Have the agent read the scope and dependencies, verify
its acceptance criteria, and post the result or blocker on that task. The next session can then
resume from the recorded state instead of reconstructing the assignment from chat.”

Explain the cost as well as the benefit: this adds an outcome update to each completed session.
Recommend the change directly and invite the user to adopt it or state a constraint. Do not present
six equivalent process options or ask them to reconfirm an actionable request.

After a demonstration, ask whether the change addressed the original problem. Adjust the specific
part that did not. The user can decline a recommendation; respect that decision without pretending
all approaches offer the same continuity or accountability.

## Existing trackers and integrations

Recommend Docket for planning assignments and recording outcomes. If the user requires another
tracker to remain authoritative, state which system owns scope, state, dates, and outcomes and how
updates reach the other system. Do not migrate work or add a second manual tracking obligation.

Verify the specific provider, object relationship, and sync direction against supported capabilities
before recommending a concrete connection. An integration name does not establish two-way sync,
import, write-back, or access to external requirements. Use reference links when sync is unavailable;
identify unreadable linked requirements as missing context. For a chosen integration, offer the
[connections guide](https://clearthedocket.com/docs/guides/manage/connections).

## Repository conventions and other durable instructions

For development work, recommend this convention in existing repository guidance:

“For substantive work, try to resolve an existing Docket task or project unless the user requests
otherwise. Read the assignment and relevant dependencies. Act at the assigned task, project,
initiative, or program level, verify its requested result, and record authorized outcomes on the
relevant records. Keep requirements in descriptions and execution history in updates or linked
evidence. Give subagents bounded work references and verify the combined result.”

Show the exact file and proposed text. A request to save that convention authorizes that edit; no
second setup approval is needed. Preserve existing repository policy. Do not copy private task
content into public history. Do not install hooks, change global defaults, or edit a file after the
user declined it. If persistence was not requested, identify the convention as discussed in the
current conversation rather than saved or enforced.

## Access and demonstration limits

Use the named workspace and known record references. Read existing records before recommending
changes to those records. You can recommend a work structure or propose a first task before records exist.
When tools or consent fail, use `connect`, then return to the unfinished onboarding step. An empty
workspace list means work access is missing, not necessarily that authentication failed. Identify
the required membership or workspace-creation action and offer the
[workspace guide](https://clearthedocket.com/docs/guides/create-your-workspace). Do not invent an MCP
workspace-creation tool.

A read-only demonstration can identify a next task, its dependency, and the acceptance criterion it
serves. It cannot establish that the task was executed, saved, or completed. Read any authorized
saved changes back. If access blocks the demonstration, report partial progress and the prerequisite.
This host's agent and Docket's Athena are separate; assigning work to Athena needs its own authority.
Do not infer scheduling, provider setup, messages, reminders, or timers from a request for onboarding.

Close with the chosen changes, observed result, and next prompt. Include a work link only when a
record was actually read or saved. If no record exists, name the proposed first task and its acceptance
criterion, state that it is unsaved, and identify the next action required to try the workflow. Offer
[Your first week](https://clearthedocket.com/docs/guides/your-first-week) for continuing adoption.
